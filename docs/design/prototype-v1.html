Design notes for PM review — v7

  • New in v7 — Real video support added to the v6 internal-tool shell (2026-08-30), status: draft, first pass, not yet reviewed. This is additive only — the v6 sidebar/topbar/footer shell, both nav lists' existing items, and every other screen are untouched; per the Business Dashboard incident (see docs/decisions.md's "shipped without a design pass" entry), this got a real design pass before any build work, same as v6 did.

    Business Dashboard → new "Videos" nav item, placed between Products and Analytics (Overview / Business Profile / Products / Videos / Analytics Soon / Orders Soon) — video sits with the other content-you-manage items, ahead of the two not-yet-built placeholders. Content is a card grid, not a data table like Products — a video's thumbnail is the point, so each card gets the same out-of-focus-footage thumb treatment (grain/bokeh/vignette + duration badge) used everywhere else in the app, not shrunk to a small square icon. Each card shows the thumb, title, the exact pending/approved/rejected .status-pill used by Products and Business Moderation (a rejected card also surfaces its rejection reason inline), view count, and a linked-product chip when one was set at upload. Upload video opens a sheet — file picker (a real native file input behind a styled dropzone; filename+size shown once picked, no real upload target, same "wired at build time" honesty as every other stubbed action in this file), title (required), description, category and "link to a product" (both optional, product list scoped to the current business) — this is the one genuinely new interactive flow in this pass, not a stub: submitting pushes a real pending video into the shared data, so it shows up immediately both in this grid and in the Admin Panel's new Video Moderation queue. Edit intentionally stays a stub (identical "not in this sprint" toast Products' own Edit button already uses) — no working edit form exists for Products either, and building one only for Videos would be inconsistent, not extra credit. Remove is a real two-click soft-delete (button turns solid red "Confirm remove?" for 4s, then removes on a second click) — deliberately named and shaped to match the "two-click-remove" pattern already shipped in the real product-management build per docs/decisions.md, so this design stays consistent with what's already live, not just internally consistent with itself. The Overview's "Videos" KPI card is now computed live from the same video list (previously a static fixture field) so an upload or a removal visibly moves the number right next to where it happened.

    Admin Panel → new "Video Moderation" nav item, placed after Product Moderation (Overview / Business Moderation / Product Moderation / Video Moderation) — mirrors Business/Product Moderation's exact tab pattern (Pending / Approved / Rejected, with a live count in each tab label) and table layout. Each row gives a moderator enough to judge without leaving the table: a real video-still thumbnail (not the small square icon business/product rows use), title, business name, "Submitted N days ago", and a one-line clamp of the submitted description. Approve is one click, same as Business/Product Moderation. Reject is the one deliberate departure from mirroring those exactly: instead of rejecting instantly with no reason (what Business/Product Moderation still do today), it opens a small sheet requiring a reason before it will submit — a reason field reuses the exact same .field/.err-msg/setFieldError validation as every form already in this file. Rationale flagged for the PM: asking a business to re-shoot or re-edit a video is a much bigger ask than fixing a product field, so a silent reject felt like it'd generate support tickets instead of resubmissions — worth considering backporting reason-capture to Business/Product reject too, but that's a call for the PM, not something changed unasked in this pass.

    Admin Overview — the "Needs your review" combined queue now interleaves pending videos with pending businesses/products, and this pass made the "oldest submissions first" copy actually true: previously the queue just concatenated businesses then products with no real sort (it only ever looked ordered because there was exactly one pending item of each). A submittedDaysAgo field now drives a real sort across all three types, so e.g. a business pending 6 days shows above a video pending 5 days, which shows above a product pending 4 days, which shows above a video pending 2 days — a real interleaved order, not three stacked lists. Added a 5th KPI card, Pending Videos, alongside the existing Pending Businesses/Pending Products/Verified Businesses/Live Categories cards; the KPI grid's desktop CSS moved from a hardcoded 4-column grid to auto-fit so both this 5-card Overview and the Business Dashboard's unchanged 4-card Overview reflow correctly from one shared rule. The sidebar's amber pending-count badge pattern (already on Business/Product Moderation) now also applies to Video Moderation, same mechanism, no new code path.

    Demo data added, matching the existing fixture's real Kenyan-business voice rather than lorem ipsum: two pending videos — AquaTank's "Tank Installation Walkthrough — Nairobi Site" (linked to the 10,000L tank product, submitted 5 days ago) and BuildRight's "Choosing the Right Hardware for Your Build" (linked to the hardware starter kit, submitted 2 days ago, on the same already-pending business used to demo Business/Product Moderation) — plus one rejected video, SunFlow's "Why Our Panels Outlast Cheap Imports", with a realistic rejection reason (unsubstantiated comparative claims) to demonstrate that state without needing a live rejection first. BuildRight's business and its pending product listing both picked up a submittedDaysAgo (6 and 4 respectively) purely so the new real sort has real numbers to work with.

    Judgment call to flag for the PM: pending/rejected videos are deliberately visible on their business's public profile "Videos" tab and in search, with only their status badge marking them as not-yet-live — this matches how pending products and unverified/pending businesses already behave everywhere else in this prototype (nothing is actually hidden pre-approval; everything is shown, clearly labelled). Flagging because a real backend would more likely hide unapproved content entirely from public listing pages and only show it to the owner/admin — if that's the intended real behaviour, it's a pre-existing gap that applies equally to pending products and unverified businesses today, not something new to video, and probably worth one consolidated fix rather than three separate ones.

    Component states added to the design system by this pass (for reuse beyond video): <textarea> and <select> now share the exact same field/focus/error styling <input> already had (previously undefined — this file had no styled select or textarea anywhere before the upload form needed one); a dashed-border .filedrop file-picker component (default/hover/has-file/error states); a .pill-danger variant for destructive confirmations (reject sheet's submit) — amber/outline/ghost all read neutral-to-positive elsewhere, so a rejection needed its own tone rather than diluting one of those.

    Not yet touched, deliberately out of scope for this pass: the Video Feed screen, home "Trending videos" rail and search's "Videos" tab still read from the same fixture videos as before v7 (v1–v7) — none of the new pending/rejected demo videos were added to FEED_ORDER/TRENDING_ORDER, so the public Shorts experience is visually unchanged.
  • New in v6 — Business Dashboard & Admin Panel get a real internal-tool shell (2026-08-30), status: draft, first pass, not yet reviewed — this directly answers the rejection of the build that reused the consumer TopNav/BottomNav shell ("that's not a Dashboard… a dashboard should have a Sidebar, navbar and footer"): a brand-new layout grammar — sidebar + topbar + content + footer — deliberately distinct from every consumer screen above, which use the phone bottom-tab-bar (mobile) / marketing top-nav (desktop) pattern instead. Same tokens throughout (Egyptian Blue, amber, Space Grotesk/Inter, the shared shadow system) — this is a new IA/layout for internal tooling, not a new visual identity. ONE shared shell (renderDashSidebar() / dashTopbarHTML() / dashFooterHTML() in the script) powers both screens with role-appropriate nav config, the same way this file already shares filter-panel logic between the mobile filter sheet and the desktop filter sidebar — so Business Dashboard and Admin Panel read as one coherent product, not two off-brand one-offs.

    Sidebar — a dark, near-black rail (hardcoded #0A0F1C, not the theme-flipping --ink token — see the code comment above .dash-shell for why) with the Miles Tech wordmark + a "Business Console"/"Staff Console" subtitle, then role-appropriate nav links: Business Dashboard gets Overview, Business Profile, Products, plus Analytics and Orders shown disabled with a "Soon" tag (present so the IA feels complete without over-building features not in this sprint's scope); Admin Panel gets Overview, Business Moderation, Product Moderation, with a live amber count badge on the moderation items whenever something's pending. Persistent/sticky on desktop (≥1024px, same sticky-column mechanism as the search filter sidebar and profile info column); collapses to a left-edge slide-in drawer below that, opened via a hamburger button in the topbar — reuses the existing sheet/backdrop system wholesale (openSheet('dashDrawer')), just with a new .sheet-side modifier that slides from the left edge instead of up from the bottom, so no new interaction plumbing was needed for the drawer's open/close/backdrop behaviour.

    Topbar — a breadcrumb ("Business Dashboard / Overview") + page title on the left, a couple of quick-stat callouts (pending-count, verification status for the dashboard; pending-business/pending-product counts for the admin panel — amber-highlighted when nonzero) on the right at desktop, and the account button on the far right reusing the exact avatar-role-icon + name pattern from the consumer Account sheet (clicking it opens that same sheet, layered on top of the dashboard). Quick-stats are hidden below 1024px to keep the mobile topbar to one row.

    Footer — a single plain row ("Miles Tech Business/Staff Console — internal tool, not visible to shoppers" + Help / Back-to-Miles-Tech), sitting in normal document flow under the content rather than fixed — deliberately unlike the bold, marketing-style dark bands used for the consumer app's section rhythm (stats band, showroom band): an internal tool's footer should read as an afterthought, not a moment.

    Content area — real card/table sections, not stacked full-width blocks: KPI stat-card grid (2-up mobile, 4-up desktop) at the top of every Overview, then .dash-section cards containing either a real data table (product listings, moderation queues) or a profile/verification summary. Business Dashboard demos a business switcher (chip row, AquaTank ⇄ SunFlow) since a real owner can run more than one showroom. Admin Panel's moderation queues are functionally real, not static: Approve/Reject on BuildRight Hardware (business, pending per the real seeded demo data) and its "Builder's Hardware Starter Kit" listing (product, pending) actually mutate the shared data — approve BuildRight here and its verified badge updates live on Home, Search and its own profile screen too, the same shared BUSINESSES/PRODUCTS arrays every other screen reads from.

    Entry points, exactly as scoped — reachable from the existing Account sheet, nothing new bolted on: signed in as Business Admin, "Manage my showroom" (previously a stub toast) now opens the real dashboard; a new demo staff account (demo-admin@miles.tech / DemoAdmin123!, Platform Administrator — surfaced in the Login sheet's demo-credentials note) gets an "Admin Panel" quick-link the same way. This mirrors the real backend on purpose: Platform Admin/Content Moderator are staff-assigned, never self-registered (the Register screen already said as much before this pass), so signing in as staff is the Admin Panel's only entry point — there's deliberately no public nav item, banner or button anyone can stumble into.

    Judgment call to flag for the PM: Analytics and Orders are shown in the Business Dashboard's nav (disabled, "Soon" tag) purely so the IA reads as a finished product rather than a 3-item stub — neither has any backend or design behind it yet; say the word if they should come out entirely rather than sit disabled.

    Responsive/theme QA on this shell, completed: verified the persistent sidebar ↔ hamburger-drawer collapse right at the 1024px handoff in both directions, the drawer's open/close/backdrop-dismiss/nav-item-close behaviour, and the Admin Panel's live count badges, on both Business Dashboard and Admin Panel, in both light and dark app-theme. Confirmed the drawer is intentionally NOT theme-aware (same hardcoded near-black rail either way — see the code comment above .dash-shell) and reads correctly against both a light and a dark content area behind it. Re-confirmed the BuildRight approve/reject live-mutation (Admin Panel → Search results badge) still holds after this pass.
  • New in v5 — Register / OTP verify / Login / Forgot & reset password (2026-08-29), status: draft, first pass, not yet reviewed: replaces the old "Account" stub with the real flow now that backend auth exists (see docs/decisions.md). Built entirely inside the existing account sheet/modal chrome (bottom sheet on mobile, centred modal at ≥1024px) — zero new colour, type or component language: it reuses .sheet, .pill, .chip, .pending-note and the app's existing shadow/glass/motion tokens. Five screens: Login (email-or-phone + password, "Forgot password?" link), Register (email and/or phone, password, role picker — one screen, no wizard), OTP verify (auto-launches right after registration), and Forgot → Reset password (request screen, then a combined code + new-password screen, matching the real API's single /auth/password/reset call shape). Sign-in/Create-account is a segmented tab switch at the top rather than a separate screen, so it reads as one continuous flow, not a context jump.

    Faithful to the real backend, not just decorative: every error string is the real copy from app/api/v1/endpoints/auth.py — "Invalid credentials.", "Account is disabled.", "Please verify your account with the code sent at registration before logging in.", "An account with this email already exists.", "Password must be at least 8 characters.", "Invalid or expired code.". Forgot password always shows the same generic success banner whether or not the account exists, and only actually offers a working code when one does — mirrors the real endpoint's deliberate anti-enumeration design (see docs/decisions.md), which is also why Login intentionally does NOT say "no account found" even though that copy was suggested as an example — using it there would contradict the backend's documented security decision; a friendlier "No account found" analogue only appears on the registration-OTP-resend edge case, matching the real /auth/otp/request 404. OTP verify does not auto-sign-in — it sends you to Login, exactly like the real API (/auth/otp/verify and /auth/login are separate calls); only password reset auto-signs-in, because the real endpoint doubles as login. Rate limiting is simulated too: a live 60-second resend countdown, a 5-resend cap, and a 5-attempt cap on wrong codes before forcing a fresh code — all matching the real numbers in app/services/otp_service.py.

    Component states covered: default/hover/focus (brand-blue focus ring on every input), inline field errors + a persistent form-level banner for account-level failures, a loading state on every submit button (spinner + "Verifying…"/"Signing in…" copy, inputs disabled), a shake-and-red-border error state on the OTP boxes, and a signed-in "home" state (avatar, role chip, verified badge, role-specific quick links, sign out). OTP entry is 6 auto-advancing digit boxes with paste support, not a single text field — the small extra interactivity is deliberate for a video-first, thumb-driven product.

    Two demo accounts pre-seeded so the flow is testable without registering: demo-owner@miles.tech / DemoPass123! (verified, Business Admin) and grace@example.com / Passw0rd! (unverified — demonstrates the "please verify" login state and its Resend-code action). Both credentials are surfaced directly in the Login sheet.

    Judgment calls to flag for the PM: (1) role picker uses selectable cards, not a dropdown — consistent with the app's tactile chip/pill language, but a 5-option dropdown would be more compact if visual weight is a concern; General User is shown full-width/first since it's the default, the other four (Business Admin, Advertiser, Content Creator, Publisher) sit in a 2×2 grid below. (2) Login and Forgot-password use a single unified "email or phone" field (auto-detected), while Register keeps them as two separate optional fields — an intentional asymmetry (Register needs to know which fields are filled to satisfy "at least one required"; Login/Forgot just need to route to a password/OTP check). (3) The on-screen "dev preview" OTP code boxes are a prototype-only testing convenience, directly mirroring the real backend's own DEBUG-only OTP echo (settings.DEBUG in app/api/v1/endpoints/auth.py) — flagging explicitly so it's never mistaken for intended production behaviour. (4) Signing out returns to the Login view without closing the sheet, keeping the user in context rather than dismissing it.
  • New in v4 — Egyptian Blue brand-colour update (2026-08-29): the owner confirmed Egyptian Blue (#1034A6) as the brand's primary blue, replacing the deep-navy #0E1729 that previously did double duty as both the brand colour and the app's dark-surface colour. Nav/IA/layout from v2–v3 are untouched — this is a token-level colour pass. Because Egyptian Blue is a vivid, mid-tone colour (36% lightness) and not dark enough to hold contrast as a background fill, it was not a find-and-replace: every old-navy usage was audited individually and split into two roles — Egyptian Blue (--brand-blue) for brand moments — logo/brand-lockup (desktop top nav wordmark), the hero gradient, active/selected states (bottom-nav active icon, active search tab, active category chip, "added to compare" chip), the Feed tab's FAB, the feed creator-avatar accent, and the "Featured" business tag — versus a genuinely dark, near-black ink (--ink, #0A0F1C, blue-tinted) for real dark surfaces/backgrounds where Egyptian Blue would lose legibility — the "Featured businesses" dark showroom band, the stats band, the home footer band, the feed's base background, the floating compare-tray and toast pills, and the dark-outlined secondary pill button. Plain body/heading text on light surfaces (search input text, card titles) also now resolves to the new ink value rather than old navy, since that role was always "near-black text," not a brand-colour moment. Amber accents sitting on top of Egyptian Blue (the FAB's play icon, the "Featured" tag's dot) were contrast-checked — Egyptian Blue is lighter/more saturated than the old navy, so amber-on-brand-blue contrast is ~6:1 versus the old ~10.5:1; still comfortably above the ~4.5:1 floor for small UI accents, but noticeably closer to the line, so flag if it ever needs a bolder amber or a drop shadow behind it. White/ice text and icons on Egyptian Blue (chips, tags, tab pills) measure ~10:1 — no concern there. Verified in both the light and dark app-theme and at both breakpoints. The six thumbnail "out-of-focus footage" gradients (.grad-0….grad-5) were deliberately left alone — those are decorative video-still art direction, not brand chrome, and weren't part of this audit.
  • New in v3 — real desktop breakpoint (≥1024px): resize this window (or the browser) past ~1024px wide. Below that, this is still the exact v2 phone-in-bezel build, untouched. At and above it, the bezel/notch/status bar/bottom tab bar disappear and a persistent top nav takes over — per the brief's architecture section, "Web application" and "Mobile-first responsive interface" are related but distinct surfaces, and this is the first pass at the former. Every screen was reflowed for the extra width, not just centred/stretched: Home gets a wider hero and the category rail, trending-videos rail and featured-businesses rail become real multi-column grids instead of horizontal-scroll-only, alongside a 6-column "Explore categories" grid. Search gains a persistent filter sidebar (same filter state/markup as the mobile filter sheet, just always visible) beside a multi-column results grid instead of one stacked list. Video feed becomes a centred, narrower vertical column — closer to YouTube Shorts/TikTok's desktop web treatment than a stretched phone screen — with a live "Up next" rail alongside it that highlights the currently-playing Short as you scroll and jumps the feed on click. Business profile and product detail both go two-column: profile splits into a sticky info sidebar (identity/stats/contact actions) beside a wider Products/Videos/About tab column; product splits into a sticky gallery beside specs/price/supplier/related-products. Bottom sheets (filter/account/compare) become centred modal panels at this width instead of bottom sheets, since a sheet sliding up from the bottom of a browser window reads as a mobile pattern. Compare tray, sponsored/featured labelling, verification badges, light/dark toggle and all interaction logic are unchanged — this is a layout pass, not a new visual direction.
  • Status: Navigation, IA and interaction model are approved and unchanged in this pass — every screen, transition and gesture from v1 is intact. This revision is a visual-execution pass only, responding to "not premium enough" + "doesn't feel video-first enough."
  • Thumbnails, before → after: every video/product tile was a flat two-stop gradient + one centered emoji — the single biggest reason it read as a wireframe. Now each tile layers a multi-stop angled gradient with two off-axis "bokeh" glows, a film-grain texture (SVG turbulence, blended at low opacity), and a bottom vignette — closer to an out-of-focus video still than a colour chip. Icons remain as placeholders for real thumbnails/photos, unchanged in role.
  • Video-specific cues added: duration badges on every video tile (home rail, search results, profile videos tab); a looping scrub-bar under the feed's progress dots so the current Short visibly "plays"; a pulsing ring on the creator avatar for the in-view feed slide; a small animated equalizer next to "Shorts" in the feed topbar. None of this is decorative-only — it's the vocabulary that signals "this is a real video" at a glance.
  • Depth & glass, before → after: chrome that used to sit on flat opaque backgrounds — bottom nav, search header, filter tabs, profile tabs, product top bar, sheets — now uses frosted blur + translucency, echoing the feed rail's existing glass treatment so the whole app feels like one material system. Cards moved from a single flat shadow to a two-layer ambient+key shadow (see --shadow / --shadow-lg) that intensifies on hover/press instead of just shifting position.
  • Typographic contrast: hero headline, section titles, stat numbers and product price all stepped up in size and tightened in tracking (negative letter-spacing on display type) for a punchier display/body split — the brief for a video-first consumer app reads bigger and bolder than a B2B density-first one.
  • Bolder, more intentional colour placement: the "Featured businesses / Digital showrooms" row is now a dark navy showroom band (grain + teal glow, frosted-glass business cards) instead of a pale-grey tint — restores the brief's alternating dark/light rhythm, which the flat build had lost. Amber CTAs got a gloss gradient + glow instead of a flat fill; the compare tray, FAB and stat numbers pick up matching amber glow so paid/primary actions feel more alive without diluting amber's meaning (still reserved for CTA + Sponsored/Featured).
  • Small bug fix along the way: the home search button, the search-screen's back/search/filter icons were rendering as blank circles (icons were never filled in on load) — filled in, no behaviour change.
  • Sponsored stays legible and distinct: unchanged semantics — amber "Sponsored"/"Featured" tags, separate labelled row in search — now with a left accent bar and soft glow on sponsored result cards so the paid placement reads as a considered treatment, not just a tinted background.
  • Verification states: unchanged — teal check = verified, grey clock = pending. Search "construction" or "hardware" to see the pending state (BuildRight Hardware).
  • Compare remains the persistent cross-screen tray (up to 3 products) — untouched per the approved interaction model.
  • Account tab now opens the full Login/Register/Verify/Reset flow described above (v5) — only the location picker remains stubbed with a toast.
