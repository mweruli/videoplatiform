# Architecture Decisions

Decisions made outside `DEVELOPMENT_PLAN.md` during implementation, so the team doesn't rediscover the same question. Append, don't rewrite history — add new entries below existing ones.

## 2026-08-28 — Sprint 1 foundations skeleton

**Sync SQLAlchemy (psycopg 3), not async.** The dev plan specifies SQLAlchemy 2.0 without committing to sync or async. Chose sync: this is a 5-person team shipping mostly CRUD-shaped endpoints in 12 weeks, and sync SQLAlchemy + Alembic is materially less error-prone than async SQLAlchemy (session lifecycle, greenlet quirks, async-aware everything) for that profile of work. FastAPI still serves requests concurrently via its threadpool. Revisit per-endpoint only if a specific route is a proven bottleneck — don't rewrite the whole data layer speculatively.

**Dependency management via requirements.txt / requirements-dev.txt, not Poetry/PDM.** Simplest thing that works, matches the Dockerfile directly, no lockfile tooling to teach. `requirements-dev.txt` adds pytest/ruff/mypy on top of the runtime set.

**Health check at both `/health` (unprefixed) and implicitly reachable via the same handler under `/api/v1`.** Unprefixed `/health` exists for load balancers, uptime monitors (see `docs/SETUP.md` re: UptimeRobot) and the frontend's placeholder connectivity check — those shouldn't need to know the API version prefix. Actual API capabilities live under `/api/v1/*` per the API-first architecture.

**Category model + migration included in the Sprint 1 skeleton**, seeded with the 18 launch categories from `PROJECT_BRIEF.md`, because the sprint plan explicitly lists "18 categories seeded" as a Sprint 1 deliverable and it's the natural way to prove the SQLAlchemy → Alembic → Postgres pipeline actually works end to end (rather than shipping migrations with zero tables). The Backend Engineer should extend this model (hierarchy, icon, sort order) as listing work in Sprint 2 needs it — treat the current shape as a placeholder, not a final schema.

**Tailwind v4 (`@tailwindcss/vite` plugin) instead of v3 + postcss config.** Less config surface for a fresh Vite project, same utility classes the Frontend Engineer and UI/UX Designer will use. `frontend/src/styles/index.css` defines a handful of starter `@theme` tokens (`--color-brand-*`, `--color-surface`, `--color-ink`) purely so the placeholder pages aren't unstyled — the UI/UX Designer owns the real design system and should replace these once Sprint 1–2 mockups are approved, not treat them as final.

**React pinned to 18.3.x**, not the 19.x that `npm create vite@latest` scaffolds by default today, to match the stack choice in `DEVELOPMENT_PLAN.md` exactly (React 18). If the team wants to move to 19 later, that's a deliberate upgrade decision, not a default from re-scaffolding.

**oxlint kept as the frontend linter** (what the Vite scaffold ships with today) rather than swapping to ESLint. It's fast and already wired to `npm run lint`, which is all CI needs; nothing in the dev plan mandates ESLint specifically. Revisit if a rule ESLint has and oxlint doesn't becomes a real blocker.

**Local dev docker-compose self-hosts Meilisearch** (official image, no external account) so `docker compose up` works with zero external signups. `docs/SETUP.md` flags the production decision (self-host vs. Meilisearch Cloud) as something the PM decides before Sprint 4, not something already settled.

**docker-compose maps Postgres to host port 5433, not 5432.** Verifying the stack on the tech lead's dev machine surfaced a real gotcha: a native Postgres service already listening on 5432 (unrelated to this project — common on a shared dev box) silently intercepts connections meant for the Dockerized one, causing confusing auth failures that look like a docker-compose bug but aren't. Container-to-container traffic (backend service to `postgres:5432`) is unaffected — only the host-exposed port moved. If you hit `password authentication failed` against `localhost:5432` on your own machine, this is almost certainly why; check `netstat`/`lsof` for another Postgres already bound there.

**Meilisearch compose healthcheck uses `127.0.0.1`, not `localhost`.** The official image's `wget` resolved `localhost` to the IPv6 loopback (`::1`) while Meilisearch itself only binds the IPv4 `0.0.0.0:7700` listener, so the healthcheck reported "unhealthy" (connection refused) even though the server was up and serving requests fine on IPv4. Same class of bug to watch for in any other container healthcheck that uses `localhost`.

**Local dev OTP provider defaults to `console`** (prints codes to backend logs) rather than requiring a real SMS/email provider account to run the skeleton. `AFRICASTALKING_*` config exists for when the Backend Engineer wires up real OTP delivery in Sprint 1's auth work — Africa's Talking is the default suggested provider given the Kenya market, but this isn't a locked-in vendor decision.

## 2026-08-29 — Sprint 2: Business & Product core

**Gap found: real auth (registration/OTP/login/JWT) was never actually built in Sprint 1**, despite `DEVELOPMENT_PLAN.md`'s sprint table listing "auth (OTP/JWT)" under Sprint 1. Only the `Category` model and health check exist from that sprint. Sprint 2's ownership model (a business has an `owner`, product/business CRUD is RBAC-gated) can't work with zero `User` model or way to authenticate. Rather than block Sprint 2 on the full OTP flow, this sprint adds the smallest thing that unblocks it:
- `app/models/user.py` — a real `users` table (phone + email, nullable role default `general_user`, the 7 brief roles as a `UserRole` enum) meant to be the permanent users table, not a placeholder to be replaced.
- `app/core/security.py` / `app/api/deps.py` — JWT issuance/verification and `get_current_user` / `require_roles` dependencies, reusable once real login exists.
- `app/api/v1/endpoints/auth_dev.py` — a **DEBUG-only** `POST /api/v1/dev/token` that creates-or-fetches a user by email/phone and mints a real access token for them, purely so Sprint 2's endpoints are exercisable end to end without registration/OTP existing yet. Hard-404s when `settings.DEBUG` is false, so it can never reach production by accident. **This should be deleted once real registration + phone/email OTP + login ships** — nothing else in the codebase depends on it (all other endpoints just consume the standard `Authorization: Bearer <jwt>` + `get_current_user`/`require_roles` contract, which real login will also produce).
- Flag for the Tech Lead/PM: auth is now the most load-bearing gap blocking a real demo (an actual person still can't register/log in) — worth prioritising ahead of or alongside Sprint 3.

**Business has a single primary location (county/city/address_line), not a multi-branch model.** `PROJECT_BRIEF.md` says "locations" (plural) but the design prototype's mock data and Sprint 2's scope both model one location per business. A proper multi-branch `BusinessLocation` table is a reasonable fast-follow once a real business asks for it.

**Business has one `category_id` (single FK), not a many-to-many.** The design prototype's mock data shows a business with two categories (`['Manufacturing','Construction']`), but the brief's field list says "industry/category" (singular). Products carry their own optional `category_id` independent of the owning business's, which covers most "we sell into two industries" cases without a business-category join table.

**Verification is a 2-step state machine**: business created as `unverified` -> owner calls `POST /businesses/{id}/submit-for-verification` -> `pending` -> moderator/admin calls `POST /admin/businesses/{id}/approve` or `/reject` -> `verified` or `rejected` (owner can resubmit from `rejected`). Approve/reject only succeed from `pending` (409 otherwise) — this is a real state machine, not a free-form status field, so the admin dashboard can't accidentally skip review.

**Editing an already-approved product resets it to `moderation_status=pending`** (admin edits are exempt). This means an owner fixing a typo temporarily un-publishes their own listing until re-reviewed. Chosen because PROJECT_BRIEF.md's Content Moderation section says *all* UGC/commercial content is reviewed before publication, and "reviewed once, then silently editable forever" undermines that. Flagging this because it has real moderator-workload implications once there's meaningful edit volume — easy to relax later (e.g. only re-review if price/name/specs change, not description typos) if it turns out to be too strict.

**Product `related_products` is an explicit curated many-to-many**, not an auto-computed "same business" list — a business can point a spare part at its parent equipment across categories. `GET /products/{id}` falls back to same-business approved products when nothing's curated, so the frontend always gets a non-empty rail without extra client-side logic.

**Object storage abstraction (`app/services/storage.py`) ships now, R2/Spaces account still doesn't exist.** `StorageBackend` is an ABC with `LocalDiskStorage` (writes under `backend/media/`, served via a `StaticFiles` mount at `/media`) and a fully-implemented `S3CompatibleStorage` (boto3, works against either R2 or DO Spaces — both speak S3) gated behind `settings.OBJECT_STORAGE_ACCESS_KEY` being set. Local disk is dev-only and gitignored; going live is a config change (fill in `OBJECT_STORAGE_*` in `.env`), not a code change.

**All new UUID-keyed tables (`users`, `businesses`, `products`, plus the `product_related` join table) use client-generated UUID primary keys**, matching the existing `categories` table's philosophy of "keep it simple" but diverging from its integer-serial choice — UUIDs avoid enumerable business/product ids in public URLs (`GET /businesses/{id}`) at negligible cost for this data volume. `slug` columns exist alongside for human-friendly URLs (`GET /businesses/slug/{slug}`).

**Enums stored as `VARCHAR` + Python-side `Enum` (`native_enum=False`), not native Postgres `ENUM` types** — consistent with wanting roles/statuses to stay admin-configurable later (per `PROJECT_BRIEF.md`'s "configurable admin roles") without an `ALTER TYPE ... ADD VALUE` migration each time a new status/role is needed.

## 2026-08-29 — Sprint 2 auth follow-up: real registration/OTP/login/password-reset

Real auth now exists (`app/api/v1/endpoints/auth.py`), replacing `app/api/v1/endpoints/auth_dev.py`'s DEBUG-only stub as the actual way a person registers and logs in. `auth_dev.py` itself is **not deleted yet** — kept as a DEBUG-only convenience for quickly minting tokens while testing other endpoints — but nothing in `app/api/deps.py` or any business/product endpoint depends on it specifically; they all consume the same `Authorization: Bearer <jwt>` contract real login now also produces.

**Login method: password is primary, OTP proves contact ownership (registration + password reset), not day-to-day login.** Considered "OTP-only" (fully passwordless) and "both, pick one at login time." Went with password-primary because:
- No real SMS/email provider account exists yet (`OTP_PROVIDER=console` — see docs/SETUP.md); an OTP-only login means *every* login depends on that provider working and being fast, which is a much bigger blast radius than needing it only at registration/password-reset time.
- SMS costs money per send in production; password login has zero per-login marginal cost.
- Password + bcrypt (`passlib`, already in requirements.txt) is a well-understood, standard mechanism the team doesn't have to relitigate later.
- OTP still does real work: it's the only thing that proves a phone/email actually belongs to the registrant (`is_verified` only flips true after a correct REGISTRATION-purpose code), and it gates password reset (`PASSWORD_RESET` purpose) so an attacker can't reset a password without access to the registered phone/email.
- `OtpPurpose.LOGIN` is scaffolded in `app/models/otp.py` but unused — a passless/OTP-login endpoint is a reasonable Phase 1b addition once a real, cost-acceptable SMS provider is wired in (see below), not a redesign.

**Endpoints shipped** (all under `/api/v1`, see `app/api/v1/endpoints/auth.py`):
- `POST /auth/register` — email and/or phone + password (+ optional full_name/role). Role is restricted to `SELF_REGISTERABLE_ROLES` (general_user, business_admin, advertiser, content_creator, publisher) — `platform_admin`/`content_moderator` are staff-assigned only, never self-registered. Creates the user `is_verified=False` and immediately issues a REGISTRATION OTP to whichever contact was given (phone preferred if both).
- `POST /auth/otp/request` — resend a REGISTRATION (or future LOGIN) code; 400s and points callers at `/auth/password/forgot` for PASSWORD_RESET (which has different enumeration-safety semantics, see below).
- `POST /auth/otp/verify` — verify a code; on REGISTRATION success flips `user.is_verified = True`. Single generic "invalid or expired" error for wrong/expired/exhausted codes (doesn't tell a caller which).
- `POST /auth/login` — email-or-phone + password. 401 on bad credentials, 403 if the account isn't verified yet or is deactivated.
- `POST /auth/password/forgot` — always 200 with an identical generic message whether or not the account exists (prevents using it to enumerate registered emails/phones); only actually issues+sends an OTP when the account is real.
- `POST /auth/password/reset` — email-or-phone + code + new_password, verified atomically; returns a fresh access token on success (reset doubles as login, since the caller just proved contact ownership).
- `GET /auth/me` — current user from a bearer token; didn't exist before, added because the frontend needs a "who am I" call after login/refresh and it's a one-line addition on top of the existing `get_current_user` dependency.

**Real rate limiting + attempt limiting, backed by Redis + Postgres** (`app/services/otp_service.py`): a 60s resend cooldown and a 5-requests/hour cap per (purpose, destination) via Redis keys, plus a 5-wrong-guesses-per-code cap tracked on the `otp_codes` row itself (`attempt_count`) — a code that hits the cap is burned immediately rather than allowed unlimited guesses. Only the HMAC-SHA256 hash of each code is stored (`app/core/security.py: hash_otp_code`/`verify_otp_code`), never the plaintext.

**OTP delivery kept behind an `OtpSender` abstraction** (`app/services/otp.py`), deliberately mirroring `app/services/storage.py`'s `StorageBackend` pattern: `ConsoleOtpSender` (dev default, logs the code) and a scaffolded `AfricasTalkingOtpSender` that raises `NotImplementedError` until `AFRICASTALKING_USERNAME`/`AFRICASTALKING_API_KEY` are provisioned and the actual `send()` call is filled in — no endpoint code changes needed when that happens, just implement that one method and flip `OTP_PROVIDER`. Separately, the auth endpoints echo the plaintext code back in the JSON response (`otp: {code, destination, expires_in_seconds}`) **only when `settings.DEBUG` is true** — this is what makes register → verify → login testable end-to-end today without a live phone/inbox; it's `None` in every response once `DEBUG=false`.

**What a real OTP/SMS provider integration needs to slot in later** (flag for PM): an Africa's Talking (or similar) account with API credentials in `AFRICASTALKING_USERNAME`/`AFRICASTALKING_API_KEY`/`OTP_SENDER_ID`, then implement the body of `AfricasTalkingOtpSender.send()` in `app/services/otp.py` (a `pip install africastalking` + a couple of lines — the call shape is already sketched in a comment there) and set `OTP_SMS_PROVIDER=africastalking` in the environment. No schema or endpoint changes are needed either way.

**Update, 2026-08-29 (later same day) — real email OTP delivery + per-channel provider split.** The PM provided a working SMTP account (cael.co.ke mail server) for the email channel, since SMS (Africa's Talking) isn't subscribed yet. Landed:
- `settings.OTP_PROVIDER` (single setting for both channels) split into `OTP_SMS_PROVIDER` (africastalking | console, phone) and `OTP_EMAIL_PROVIDER` (smtp | console, email) — the per-channel sender split flagged as a follow-up above. `get_otp_sender()` now takes the `OtpChannel` and picks the provider setting for that channel; `otp_service.request_otp()` calls it as `get_otp_sender(channel)`.
- `SmtpOtpSender` implemented in `app/services/otp.py` via stdlib `smtplib`/`email.message.EmailMessage` (no new dependency) — sends a real OTP email (code, purpose-specific action line, expiry pulled from `OTP_TTL_MINUTES`) using `SMTP_HOST`/`PORT`/`USERNAME`/`PASSWORD`/`FROM_EMAIL`/`FROM_NAME`/`USE_TLS`. Only handles `OtpChannel.EMAIL`; raises if misconfigured or called for PHONE, same fail-loud pattern as `AfricasTalkingOtpSender`.
- Verified against the live docker-compose stack: registering with a real email address (`OTP_EMAIL_PROVIDER=smtp`) completes a real SMTP transaction (STARTTLS + auth + 250 OK from the cael.co.ke server) with no exception; registering with a phone number is unchanged (`OTP_SMS_PROVIDER=console`, code logged + DEBUG-echoed as before). Test user cleaned up from the dev DB afterward.
- `preferred_otp_channel` (nullable `OtpChannel` column on `User`, default `NULL`) added via migration ahead of the PM's near-term idea of letting a user/admin pick SMS-vs-email independent of how they registered. Schema-only for now — no endpoint reads or writes it yet, since wiring it in means threading a `User` lookup into `_channel_and_destination()` in `app/api/v1/endpoints/auth.py` (today that function only sees whatever `email`/`phone` the request payload supplied, not the account) and deciding channel-selection precedence, which is real endpoint-behavior work, not a schema change. Flagging as the actual follow-up task; the migration itself just avoids a second schema change when that's picked up.

**Bug fixed along the way, not a design decision:** `passlib[bcrypt]==1.7.4` (already in requirements.txt from Sprint 1) crashes on its very first `hash()` call with `bcrypt>=4.1` installed (`ValueError: password cannot be longer than 72 bytes`) — a known passlib/bcrypt compatibility break, unrelated to any actual password length. Pinned `bcrypt==4.0.1` explicitly in `requirements.txt` to fix it; anyone rebuilding the backend image or a fresh venv needs this pin, not a live `pip install`.

**`users.phone` is normalized before storage/lookup** (`app/utils/phone.py: normalize_phone`) — strips spaces/dashes/parens so `"+254 711 224560"` and `"+254711224560"` resolve to the same account for register/login/OTP lookups. This is separate from `app/schemas/business.py`'s existing phone regex (business contact numbers are display-only, not an identity/lookup key, and were intentionally left as-is).

## 2026-08-29 — Isolated test database (fixing repeated demo-data pollution)

**Root cause**: `app/db/session.py` builds its SQLAlchemy engine from `settings.DATABASE_URL` eagerly at import time, and every test file does `from app.main import app` at module level with no `conftest.py` in `backend/tests/` to intervene. Whatever `DATABASE_URL` happens to be set in the invoking process wins. Inside the `backend` container, `docker-compose.yml` sets `DATABASE_URL` to the real `milestech` database — the same one `app/db/seed_demo.py` seeds for the PM's demo — so every `docker compose exec backend pytest` run (explicitly asked for repeatedly, as real end-to-end verification against the live stack) was writing test businesses/products/users straight into the demo data. This had to be manually cleaned up after at least four rounds. CI was never affected — it spins up its own throwaway Postgres service per run — this was purely a local/docker-compose problem.

**Fix**: `backend/tests/conftest.py` (new file). Pytest guarantees conftest.py is imported before any test module in the same directory is collected, so this file rewrites `DATABASE_URL` (and `REDIS_URL`) in `os.environ` — to `<original db name>_test` / Redis logical DB 15 — *before* `app.core.config.settings` or `app.db.session`'s module-level engine can ever be constructed from the un-rewritten value. This is invocation-agnostic by construction: a bare venv `pytest`, `docker compose exec backend pytest`, and a hypothetical future local run against a remote dev Postgres all go through the same file and all land on the isolated database — nobody has to remember to set an env var by hand, which is exactly how this kept recurring.

A session-scoped, autouse fixture in the same file then (a) `CREATE DATABASE`s the isolated `<db>_test` database if it doesn't already exist (connecting to Postgres's always-present `postgres` maintenance DB, autocommit — cheap, one extra sibling database in the same Postgres container/instance, no new service in `docker-compose.yml`), and (b) runs `alembic upgrade head` against it before the first test executes. Both steps are idempotent, so repeated runs just no-op the second time onward.

An explicit `TEST_DATABASE_URL` (or `TEST_REDIS_URL`) env var, if set, overrides the derived default — an escape hatch for pointing tests at a wholly separate test instance later, not needed for the current setup.

**Verified against the live docker-compose stack**: ran `docker compose exec backend pytest` twice, plus once more via the local `backend/.venv`. All three runs: 24/24 tests passed, and `milestech` (the real demo DB) stayed at exactly 6 businesses / 8 products / 1 user (the real seed data) before and after every run, while `milestech_test` visibly accumulated rows across runs (empty → 7/2/23 → 14/4/46), proving the isolation is real and not just "tests still pass by coincidence."

**Same-class risk flagged, not fixed in the same pass beyond the trivial Redis DB-index swap above**: `app/services/otp_service.py`'s Redis-backed rate limiting (`otp:ratelimit:<purpose>:<destination>` keys) would have hit the same shared-dev-Redis pollution risk as Postgres — fixed trivially alongside this change by routing tests to Redis logical DB 15 instead of the dev-default DB 0 (same instance, no new service, `conftest.py` does this the same way as the Postgres DB-name swap). **Not yet addressed**: Meilisearch has no equivalent per-test-run index namespace — if/when a test suite starts writing to Meilisearch (search integration lands in Sprint 4), it will index straight into whatever index the live dev Meilisearch instance uses unless a similar isolation mechanism (a `_test`-suffixed index, cleaned up per session) is added at that time. Flagging now so the Backend Engineer doesn't have to rediscover this when Sprint 4's search work starts writing real documents from tests.

**How to run tests locally from now on** (see also `README.md`): `docker compose exec backend pytest` (or `pytest` from an activated `backend/.venv`) — no extra flags, no env vars to set. It always targets `milestech_test` (or `<your DATABASE_URL's db>_test`), never the demo database, automatically.

## 2026-08-29 — Process incident: Business Dashboard shipped without a design pass

The Business Dashboard (and the Admin Panel build immediately following it) were dispatched to the Frontend Engineer directly, on the reasoning that they were "genuinely new UI but small/contained enough to build within the existing design system, use your judgment on layout." The PM correctly rejected the result: *"That's not a Dashboard. A dashboard should have a Sidebar, navbar and footer — what I'm seeing is just a webpage."*

The mistake: reusing the consumer site's `TopNav`/`BottomNav` shell and stacking content in it is not a substitute for actual dashboard/internal-tool layout — sidebar navigation, a dedicated top bar, and a footer are a different paradigm from the public browsing shell, not a styling detail that "using the existing tokens" covers. Getting the colors/type/components right while skipping this meant the screen technically matched the design system and still completely failed on layout.

**Fix**: a real design pass for a shared internal-tool shell (sidebar + top bar + footer, role-aware nav items) covering both Business Dashboard and Admin Panel, then both get rebuilt into it — the data-fetching/mutation logic (`useDashboard.ts`, the admin queue hooks) is expected to carry over largely unchanged; this is a container/layout rebuild, not a feature rebuild. Also added an explicit rule to `.claude/agents/frontend-engineer.md`: dashboard/internal-tool screens always need a design spec, full stop — "use your judgment, stay within the design system" is not license to skip that, even when it's the orchestrator (not just the PM) who frames it that way.

## 2026-08-30 — Sprint 3: Video model, upload/moderation, VideoBackend abstraction

Backend video pipeline for PROJECT_BRIEF.md's "Video & Shorts Platform" module now exists (`app/models/video.py`, `app/api/v1/endpoints/videos.py`, admin moderation added to `app/api/v1/endpoints/admin.py`), closing Sprint 3's must-ship gap — the frontend has been running the video-first thesis on fixture data since Sprint 1.

**`VideoBackend` abstraction (`app/services/video.py`) mirrors `StorageBackend`/`OtpSender` exactly**, per the established pattern: an ABC (`upload()`/`delete()`), a working dev-default (`LocalFileVideoBackend` — writes the raw uploaded file via the same local-disk mechanism images use, served back as a plain file URL good enough for a basic HTML5 `<video>` tag; no transcoding/adaptive bitrate/thumbnail-or-duration extraction, since that needs ffmpeg which isn't a runtime dependency here), and two provider scaffolds (`CloudflareStreamBackend`, `BunnyStreamBackend`) that raise a clear `RuntimeError`/`NotImplementedError` until an account exists, with the real API call shape sketched in comments — same shape as `AfricasTalkingOtpSender`. `get_video_backend()` picks a real provider only once *both* `VIDEO_API_PROVIDER` says to use it *and* that provider's credentials are actually set (`CLOUDFLARE_ACCOUNT_ID`+`CLOUDFLARE_STREAM_API_TOKEN`, or `BUNNY_STREAM_LIBRARY_ID`+`BUNNY_STREAM_API_KEY`), otherwise it degrades to the local backend — a dev setup with the default `.env.example` config never 500s for a missing third-party account.

**Video moderation reuses `Product`'s `ModerationStatus` enum directly** (imported into `app/models/video.py`, mapped to its own `video_moderation_status` VARCHAR-backed column) rather than a parallel enum with identical `pending`/`approved`/`rejected` values — same states, no reason to duplicate the type. Upload → owner-gated (business owner or platform admin, same `_can_manage` pattern as products/businesses) → `pending` → admin/moderator `POST /admin/videos/{id}/approve|reject`, byte-for-byte the same shape as the existing business/product moderation endpoints (same `require_moderator` gate, same reject-with-reason schema, same "can only transition from pending, 409 otherwise" state machine).

**Editing an approved video resets it to `pending`** (admin edits exempt) — same policy as products, for the same Content-Moderation-section reasoning already flagged in the Sprint 2 entry above.

**`GET /videos` deliberately repeats products.py's `include_unapproved` pattern *and* its bug-fix**: `is_active` is enforced unconditionally regardless of `include_unapproved`, so an owner's soft-deleted video can't reappear in their own dashboard the way the products regression did (see `test_removed_product_stays_gone_from_owner_view`) — `test_removed_video_stays_gone_from_owner_view` guards the video equivalent from day one instead of needing a second incident to catch it.

**View counting is a dedicated `POST /videos/{id}/view` endpoint, not increment-on-GET.** `GET /videos/{id}` stays side-effect-free (no accidental inflation from link-preview bots, prefetching, or the owner's own dashboard re-fetching the record); the endpoint only increments for videos that are currently `approved` + `is_active` (404 otherwise), so a pending/rejected/removed video can't accumulate views before or after it's actually public. No per-viewer de-duplication — that's an analytics-hardening concern for later, not launch-blocking for Phase 1a's "basic counts" scope.

**A video can reference a product it showcases (`product_id`, optional), validated to belong to the *same* business as the video** (`_resolve_product()` in `app/api/v1/endpoints/videos.py`) — an endpoint-level invariant, not a DB constraint, since nothing in the schema stops a video's `product_id` FK from pointing at another business's product otherwise. Deliberately follows the "no explicit validation beyond the FK" pattern products.py already uses for `category_id`, since category assignment has no cross-business-ownership question to get wrong the way product association does.

**Seed data: 3 real (tiny, ffmpeg-generated) MP4 clips + JPG thumbnails checked into `backend/app/db/seed_assets/videos/`**, one per business referenced in `docs/decisions.md`'s existing seed set (AquaTank manufacturing, Solaris inverter demo, SunFlow irrigation) — `seed_demo.py` uploads them through the real `VideoBackend` (not a hand-written DB row pointing at a path that may not exist), so a fresh clone/CI run always has something the frontend can actually fetch and play, not just metadata. Files are ~6-9KB each (4s, 640x360, `libx264`, no audio) — generated with `ffmpeg` via the `imageio-ffmpeg` PyPI package (bundles a static binary; not a runtime dependency of the app, only used once to produce these three checked-in files) since no ffmpeg binary or managed video API account is available in this environment. The repo-wide `*.mp4`/`media/` gitignore rule now has an explicit `!backend/app/db/seed_assets/**` exception so these specific files aren't accidentally excluded.

**What a real Cloudflare Stream / Bunny Stream integration needs to slot in later** (flag for PM, same shape as the Africa's Talking OTP flag above): provision the account, fill in `CLOUDFLARE_ACCOUNT_ID`/`CLOUDFLARE_STREAM_API_TOKEN` (or `BUNNY_STREAM_LIBRARY_ID`/`BUNNY_STREAM_API_KEY`) in the environment, implement the body of that backend's `upload()`/`delete()` in `app/services/video.py` (the real API call shape is already sketched in comments — Cloudflare's direct-upload endpoint or Bunny's create-then-PUT flow), and set `VIDEO_API_PROVIDER` accordingly. ## 2026-09-04 — Phase 1a: core analytics (product/business views + impressions + owner stats) and rule-based recommendations (trending videos + category-first related products)

Closes the last two items on Phase 1a's must-ship list: "Core analytics: views, search appearances, basic counts" and "Rule-based recommendations: trending + related-by-category." **Schema**: `businesses.view_count`/`businesses.impression_count` and `products.view_count`/`products.impression_count` (all `Integer`, `nullable=False`, `default`/`server_default=0`) — migration `b2e7c5a1f8d9_core_analytics_counters.py`. No `impression_count` on `Video`: not requested by the brief, and search results in this platform are business/product-centric (a search result *is* a business or product card; videos surface via their own feed/browse, not the keyword-search results page), so there's no natural "appeared in search results" moment to hook for a video the way there is for a business/product card being rendered in a results list.

**Gap 1a — product/business view counters, mirroring Video's exactly.** `POST /products/{id}/view` and `POST /businesses/{id}/view` are byte-for-byte the same pattern as the already-shipped `POST /videos/{id}/view`: a dedicated POST (not increment-on-GET, so prefetching/bots/the owner's own dashboard re-fetching the record can't inflate it), no per-viewer de-duplication (an analytics-hardening concern, not launch-blocking per the existing Video precedent), and the endpoint 404s instead of incrementing unless the target is currently public — `is_active=True` + `moderation_status=APPROVED` for a product (matches the video check exactly), `is_active=True` + `verification_status=VERIFIED` for a business (the business equivalent of "public"). Both endpoints are unauthenticated, same as the video one — a page view is a page view regardless of who's looking.

**Gap 1b — "search appearances" via a real, honest impression signal, not a fabricated number.** Since `frontend/src/lib/searchCatalog.ts` does search ranking/matching client-side (the server never sees which N results were shown for a given query), the only way to get a real server-side "search appearances" count without moving search server-side is for the client to report it. Went with the suggested shape, with one deliberate deviation from the literal path text in the brief: **`POST /businesses/impressions` and `POST /products/impressions` — collection-level batch endpoints (no `{id}` in the path), not `POST /businesses/{id}/impressions`.** The brief's own wording ("a batch endpoint ... with the list of ids currently visible") describes a multi-id operation, which doesn't fit under a single-resource path — a literal `/businesses/{id}/impressions` batch endpoint would have an id in the URL that's redundant with (or contradicts) the ids in the body. `app/schemas/common.py`'s `ImpressionBatchRequest`/`ImpressionBatchResult` are shared between both endpoints (same shape, same reasoning, avoids two near-identical schemas). Behavior:
- Body: `{"ids": [...]}`, capped at 1–100 ids per call (empty list or >100 is a 422) — a single render showing more than 100 cards isn't realistic at this platform's scale, and the cap bounds the write regardless of client behavior.
- Each id that resolves to a real, *currently public* row (same public-visibility check as the view endpoints) gets `impression_count += 1` via a single bulk `UPDATE ... WHERE id IN (...)`, not a per-id round trip. Ids that don't exist or aren't public are silently skipped — the caller is a search-results render reporting what it drew on screen, not a user action on one specific business/product, so a stale id shouldn't fail the whole batch.
- No auth required (anonymous search is just as real a signal as logged-in search) and no per-viewer/per-session de-duplication (same "cheap and real, not analytics-hardened" bar as the view counters) — a business/product appearing 3 times across a user's pagination clicks on the same query legitimately gets 3 impressions; that's an acceptable MVP simplification, not a bug.
- Response is `{"updated": N}` (count of ids that actually matched) rather than 204 — cheap to compute from the `UPDATE`'s rowcount and gives the frontend a debugging signal if, say, it's sending ids that never match (wrong id shape, stale cache, etc.) without needing a second call.

**Gap 1c — `GET /businesses/{id}/stats`, owner/admin-only aggregate view.** Gated by the same `_can_manage` helper already used everywhere else in `businesses.py` (owner or `platform_admin`). Returns `business_view_count`, `business_impression_count`, `total_product_views` and `total_video_views` (summed across the business's own products/videos), and `product_counts`/`video_counts` broken out by `ModerationStatus` (`pending`/`approved`/`rejected`) — computed via a `GROUP BY moderation_status` aggregate query per resource type (two queries total, not N+1). Judgment call: **counts and view sums only include currently-active (not soft-deleted) products/videos** — matches `Business.product_count`'s existing "active only" convention elsewhere in this codebase, and a business owner asking "how are my listings doing" shouldn't have removed listings' stale numbers muddying the total. This is the API the frontend's already-scaffolded, currently-disabled "Analytics" nav item (`frontend/src/components/dashboardshell/DashboardShell.tsx`'s "Soon" pill) will call once the Frontend Engineer picks this up — building the endpoint only, no dashboard UI, per this round's "backend-only" scope.

**Gap 2a — `GET /videos?sort=trending`, a real trending signal.** `frontend/src/components/home/TrendingVideos.tsx`'s own code comment already flagged the honest state of things: "no trending/ranking signal on Video yet ... this takes the first TRENDING_COUNT rows as returned, i.e. most-recently-uploaded." Added `sort: Literal["recent", "trending"] = "recent"` to `GET /videos` — default unchanged (still `created_at desc`, so nothing depending on the existing order breaks), `sort=trending` orders by `view_count desc` (then `created_at desc` as a tiebreaker for equal-view videos). Judgment call: **raw all-time `view_count`, not a time-decayed score.** Considered a decay function (e.g. views-per-day-since-upload, or an exponential half-life weighting) but rejected it for now — at Phase 1a's real view volume (a handful of seeded videos, launch not yet public), a decay formula is complexity with no real signal to tune it against, and "most all-time views" is a perfectly defensible, explainable MVP definition of "trending." The frontend picking this up (swapping `TrendingVideos.tsx`'s implicit-recency read for an explicit `?sort=trending` call) is next-round frontend work, not done here (backend-only scope this round).

**Gap 2b — related-products fallback now prefers same-category over same-business.** `app/api/v1/endpoints/products.py`'s `get_product` previously fell back straight to same-business products when nothing was curated in `related_products` — a hardware store's cement and paintbrushes would show up as "related" to each other purely by having the same seller. New fallback chain (`_related_products_fallback`, first non-empty tier wins, tiers are not merged/topped-up from each other):
1. **Same-category** — any other approved+active product sharing at least one category via `product_categories`, ranked by number of shared categories (desc) then recency, limited to 3.
2. **Same-business** — the original fallback, kept as the next tier for when category data doesn't help (product has zero categories, or is the only approved product in its category).

## 2026-09-04 — Phase 1b design pass: M-Pesa self-serve payments for featured placement

Architecture/foundation pass for DEVELOPMENT_PLAN.md's first fast-follow item, "M-Pesa self-serve payments for ads" — scoped down (with the PM, already decided before this pass) to **featured placement only**: a business pays via M-Pesa STK Push to feature their business and/or one specific product for a fixed duration, reusing the existing `is_featured` bool (see the 2026-09-03 entry above) rather than a full campaign manager (budgets/targeting/date-ranges are still explicitly out of scope). This entry covers the model, migration, and `app/services/mpesa.py` shipped now; endpoint wiring is a deliberate handoff to the next backend-engineer round (see the implementation plan at the end of this entry) — same design-then-implement sequencing as this project's other cross-cutting work.

**Pricing — single placeholder constants block.** `app/core/featured_pricing.py`: `FeaturedPricingTier` enum (`SEVEN_DAYS`, `THIRTY_DAYS`) mapped to a `FeaturedPricingOption` (label, `amount_kes`, `duration_days`) in one `FEATURED_PRICING` dict. Values are **KES 500/7 days and KES 1,500/30 days** — deliberately round, obviously-fake test numbers since the PM hasn't supplied real client pricing yet; changing them later is "edit this one dict," not a hunt through endpoint code. `FeaturedPurchase` snapshots the resolved `amount_kes`/`duration_days` onto its own row at purchase time rather than live-joining this dict, so a future pricing change can never retroactively alter what a historical purchase is recorded as having cost or how long it ran.

**Data model — a dedicated `FeaturedPurchase` table (`app/models/featured_purchase.py`), not fields on Business/Product.** Reasoning: a purchase has its own lifecycle (`pending -> completed/failed`) that outlives and is independent of the business/product it targets — a failed/cancelled payment still needs a durable record for support/dispute questions ("why wasn't I featured", "I was charged but nothing happened"), and a business accumulates a purchase *history* (repeat placements) that a single set of columns on Business/Product structurally can't represent. Business/Product only need to track *current effective state*, which is the pre-existing `is_featured` bool plus one new nullable column, `featured_until`, added to both tables in the same migration.

- **One purchase = one target, expressed structurally, not via a flag.** `business_id` (required) is always the paying business; `product_id` (nullable) is set when the purchase features one specific product of that business, left `NULL` when it features the business itself. A row can never target both or neither — enforced at the endpoint layer (validate `product_id` belongs to `business_id`), the same convention this codebase already uses for `Video.product_id`'s same-business invariant (`app/api/v1/endpoints/videos.py`'s `_resolve_product()`), not a DB constraint.
- **Fields**: `initiated_by_user_id` (audit — who clicked buy, business owner or an admin acting on their behalf), `tier` + snapshotted `amount_kes`/`duration_days`, `status` (`pending`/`completed`/`failed` — a real "waiting to hear back" state, not a boolean, because STK Push is fire-and-forget-then-async-callback), `checkout_request_id` (unique+indexed — Safaricom's own correlator for the callback) + `merchant_request_id` (stored and cross-checked on callback as a second, cheap correlation factor — see the callback validation posture below), `payer_phone` (the MSISDN actually charged — explicitly supplied at purchase time, not assumed to be the account's own phone, since the payer may use a different line), `mpesa_receipt_number`/`result_code`/`failure_reason` (filled by the callback), and `featured_until` (set only once `status=completed`).
- **No "cancelled" status separate from "failed."** Daraja's STK Push failure modes (user cancels on-phone, PIN timeout, insufficient funds, network) all arrive as the same callback shape with a non-zero `ResultCode` and a `ResultDesc` string — `failure_reason` carries that description verbatim (e.g. "Request cancelled by user") so the frontend/support can show the real reason without the schema needing a parallel enum of every Safaricom result code. A cancelled/failed STK push has no "retry" path on the same row — Safaricom treats a `CheckoutRequestID` as single-use — so a user trying again is a fresh `POST` (a new row), matching how the model is built.

**Expiry mechanism — "sweep on read," not a background job.** `app/services/featured_expiry.py`: `sweep_expired_featured_businesses(db)` / `sweep_expired_featured_products(db)` each run one cheap, indexed, idempotent bulk `UPDATE ... WHERE is_featured=true AND featured_until IS NOT NULL AND featured_until <= now()` (flips both columns back), called at the top of the request in every public read path that serves or filters on `is_featured` (`GET /businesses`, `GET /businesses/{id}`, `GET /businesses/slug/{slug}`, `GET /products`, `GET /products/{id}` — wiring these calls in is part of the handoff below, not done in this pass).

Checked before deciding this, per the task brief: **no job/scheduler infra exists anywhere in this codebase as of this pass.** `requirements.txt` has neither `arq` nor `celery`; `docker-compose.yml` has no worker/beat service; nothing in `app/` imports either package. DEVELOPMENT_PLAN.md's tech-stack line ("arq/Celery for async jobs") is aspirational, not yet wired up. Introducing a whole new job-scheduler subsystem (a worker container, a queue, deployment/monitoring for it) for this one narrow need — flip a boolean once a timestamp passes — would be disproportionate new infra for a fast-follow feature and cuts against the plan's own "buy, don't build" / smallest-thing posture. The sweep-on-read approach needs zero new infra, is correct with no propagation lag (whichever request runs next self-heals the row before serving results), and keeps `is_featured` truthful in the database itself rather than only at response-serialization time — which matters for anything that ever queries it directly later without knowing about `featured_until` semantics (a future Meilisearch sync job, an analytics query, an admin export). Tradeoff, stated plainly: this is a small write on the hot GET path — negligible in practice (the `WHERE` matches zero rows the overwhelming majority of the time, and `featured_until` is indexed on both tables), but if it's ever a measurable cost at real scale, moving the identical function into a scheduled arq job is a one-file change, not a redesign.

Interaction with the pre-existing **admin-set permanent featuring** (2026-09-03 entry): admin `POST /admin/.../feature` never touches `featured_until` — it stays `NULL`, which the sweep's `WHERE featured_until IS NOT NULL` clause explicitly never matches. Admin-set featuring is therefore permanent exactly as before; only self-serve, time-limited purchases (which always set a concrete `featured_until`) are subject to the sweep. A business/product with both an active self-serve purchase *and* a later admin `unfeature` call is fully unfeatured by the admin call (existing endpoint behavior, unchanged) — the two mechanisms share one flag by design, admin action always wins immediately.

**Stacking/extension semantics (for the handoff — not yet implemented, decide-now-so-the-backend-engineer-doesn't-relitigate-it):** if a business/product already has an active `featured_until` (from a still-running earlier purchase, or a fresh admin toggle followed by a self-serve buy) and a new purchase completes, the new window should **extend from the later of `now()` or the existing `featured_until`**, not simply overwrite it with `now() + duration_days` — a business buying a second 7-day slot while 3 days remain on the first should get 10 days remaining, not 7. This is a one-line `max(existing_featured_until or now, now) + timedelta(days=duration_days)` at the point the callback handler applies a completed purchase — flagged explicitly so it's not silently skipped as "just set it."

**API shape (design only — endpoints not built in this pass, see the implementation plan below):**
- `GET /featured/pricing` — public, returns the tiers from `FEATURED_PRICING` so the frontend never hardcodes amounts/durations.
- `POST /businesses/{business_id}/featured-purchases` — owner/admin-gated (`_can_manage`, the existing pattern from `businesses.py`), body `{tier, product_id?, phone}`. Validates `product_id` (if given) belongs to `business_id`. Calls the `PaymentBackend`, and — deliberately — **only creates the `FeaturedPurchase` row after Daraja's STK Push call itself succeeds** (i.e. after a real `checkout_request_id` exists), not before. Judgment call: a synchronous Daraja failure (bad credentials, network error, rejected request — see the live "Invalid CallBackURL" finding below for a concrete example) means there is nothing a callback could ever correlate to, so a row with no `checkout_request_id` would just be dead data; better to 502 the request and create nothing than to manage a two-phase "initiating -> pending" status for a case that has no async component at all.
- `GET /featured-purchases/{id}` — owner/admin-gated, returns current `status`/`featured_until` — what the frontend polls (every 2–3s is reasonable; Daraja's own STK prompt times out client-side after roughly 60–90s if the user never responds, so a client-side poll timeout around 2 minutes with a "didn't hear back in time" message is a sane upper bound) to move the UI through "waiting for you to approve on your phone" -> success/failed without a hard reload.
- `GET /businesses/{business_id}/featured-purchases` — owner/admin-gated, paginated purchase history for that business. Lower priority than the two above; include if time allows, not a blocker.
- `POST /payments/mpesa/callback` — the Safaricom-facing webhook, necessarily unauthenticated (no bearer token, no user session — Safaricom's servers call this directly). **Validation posture, deliberately not over-engineered**: Daraja STK callbacks carry no cryptographic signature and no shared secret to check — the correlation surface is exactly `CheckoutRequestID` + `MerchantRequestID`, both Safaricom-generated, unguessable, and never exposed to any client (only Safaricom and this backend ever see them). The handler should: (1) parse with `mpesa.parse_stk_callback()`, logging-and-returning-200 (never 500) on a malformed/foreign payload; (2) look up the `FeaturedPurchase` by `checkout_request_id`, and require its `merchant_request_id` to match too — a payload with the right `checkout_request_id` but a mismatched `merchant_request_id` is logged as a rejected anomaly, not processed; (3) if no matching row, or the row is no longer `pending` (a duplicate/retried callback — Safaricom does retry), log and return 200 without reprocessing — idempotent by construction; (4) on `result_code == 0`, set `status=completed`, `mpesa_receipt_number`, `result_code`, and `featured_until` (applying the stacking rule above) and flip the target's `is_featured=True`/`featured_until`; on non-zero, set `status=failed`, `result_code`, `failure_reason=result_desc`. **Always return HTTP 200 with a `{"ResultCode": 0, "ResultDesc": "Accepted"}` body regardless of internal outcome** — this is Daraja's documented callback-ack contract; a business-logic `failed` purchase is a legitimate terminal state, not a delivery failure, and returning anything but 200 makes Safaricom retry-storm the endpoint. **Follow-up flagged for the Tech Lead/PM, not blocking this feature**: once the callback URL is live on a real production domain, add a Cloudflare WAF/IP-allowlist rule scoped to Safaricom's published IP ranges as defense-in-depth — that's infra-layer hardening, independent of and in addition to the app-layer correlation check above, not required to ship the feature.
- Amount cross-check: log a warning (not a hard rejection) if the callback's `CallbackMetadata` `Amount` differs from the purchase's stored `amount_kes` — treated as a monitoring signal, not a gate, since rejecting outright on a rounding/currency artifact risks stranding a legitimate payment.

**`app/services/mpesa.py` — shipped this pass, live-verified (see below).** Mirrors `StorageBackend`/`OtpSender`/`VideoBackend`'s exact established shape: a `PaymentBackend` interface, one real implementation (`DarajaMpesaBackend`), a `get_payment_backend()` factory. One deliberate deviation from that pattern, documented in the module: **sandbox vs. production Daraja is a `settings.MPESA_ENV` branch inside one class, not two classes** — unlike Cloudflare Stream vs. Bunny Stream (genuinely different SDKs), Daraja sandbox and production are the same API family differing only in base URL/live credentials, so two near-identical classes would be speculative duplication. A future non-M-Pesa rail (BunnyPay, a card processor) is a new `PaymentBackend` subclass + a `PAYMENT_PROVIDER` setting branch in `get_payment_backend()` — no calling-code changes, exactly like swapping `VIDEO_API_PROVIDER`.

Contents: OAuth token fetch (`_fetch_access_token`) + Redis-backed caching (`_get_access_token`, key `mpesa:oauth_token:<env>`, TTL = Daraja's `expires_in` minus a 60s safety margin) so every uvicorn worker/replica shares one token instead of each independently hitting Daraja's OAuth endpoint — same rationale as `otp_service.py`'s existing Redis-backed rate limiting, reusing `app/db/redis.py`'s `get_redis_client()`; `initiate_stk_push()` (builds the `Password`/`Timestamp` pair using `Africa/Nairobi` local time explicitly, not UTC or server-local time, since Daraja validates the timestamp against Kenya time — verified this matters, not a guess); `parse_stk_callback()`, the helper the callback handler needs to turn Safaricom's `Body.stkCallback.CallbackMetadata.Item` array-of-`{Name,Value}` shape into a plain `StkCallbackResult` dataclass; and `to_msisdn()`, normalizing `0711...`/`+254711...`/`254711...`/`711...` input phone shapes into Daraja's required `254711224560` MSISDN format (raises `MpesaError` for anything that doesn't resolve, rather than sending Safaricom a malformed number and getting an opaque 400 back).

## 2026-09-04 — Phase 1b design pass: self-serve advertiser campaign manager

Architecture/foundation pass for DEVELOPMENT_PLAN.md's second fast-follow item, "self-serve advertiser campaign manager" — genuinely more than the already-shipped Featured Placement (flat-fee, untargeted, duration-based; see the 2026-09-04 "M-Pesa self-serve payments for featured placement" entry above) per PROJECT_BRIEF.md's Digital Advertising bullet's explicit call for "location- and category-based targeting" and "full campaigns" with impression/click "campaign performance" reporting. Same sequencing as that round: models + migration + a `campaign_billing.py`-shaped service ship now, live-verified; FastAPI endpoints and all frontend work are a deliberate handoff (implementation plan at the end of this entry).

**Scope decided with the PM already, not re-litigated here:**
1. Only business owners (the existing `_can_manage` ownership model — owner or `platform_admin`, byte-for-byte the same gate as businesses.py/products.py/videos.py/featured_purchases.py) can create/manage a campaign. The dormant `advertiser` `UserRole` (self-registerable per `app/schemas/auth.py`'s `SELF_REGISTERABLE_ROLES`, with stub "Ad campaigns"/"Billing" quick-links in `frontend/src/components/auth/views/AccountHomeView.tsx`'s `ROLE_QUICK_LINKS`) stays dormant — **explicitly not wired into any permission check this round.** This is a deliberate non-decision, not an oversight: introducing a second, narrower permission class (advertiser-role-gated campaigns vs. owner-gated everything-else) would fork this codebase's one consistent ownership model into two for a role that has no other wired behavior anywhere yet (no advertiser-specific dashboard, no separate advertiser-vs-business-owner distinction in any existing screen). Revisit once there's an actual product reason an `advertiser` needs to manage a campaign for a business they don't own.
2. Real prepaid budget depletion (impressions bill against `budget_kes`, auto-exhausting at zero) — the PM's explicit choice over a simpler targeted-flat-fee alternative.

**Data model** (`app/models/campaign.py`, `app/models/campaign_funding.py`):

- **One campaign = one target, reusing `FeaturedPurchase`'s exact structural convention** — `business_id` (required, the paying/owning business) + `product_id` (nullable; NULL = promotes the business itself, set = promotes one specific product of that business). Endpoint-enforced (validate `product_id` belongs to `business_id`), not a DB constraint — same precedent as `Video.product_id` and `FeaturedPurchase.product_id`. Deliberately not inventing a different convention for a third feature that has the identical shape.
- **Targeting reuses existing fields, no new geography/category concepts**: `category_id` (nullable FK to `categories`, NULL = all categories) and `county` (nullable free-text string, NULL = all locations) — exactly `Business.category_id`/`Business.county`/`Product.county`'s own types and null-semantics, not a new targeting-specific model. A campaign's targeting is an independent advertiser choice and is **not required to match the target's own category/location** (e.g. a business in "Retail" can target category "Construction") — the platform doesn't gate targeting by organic relevance; see the ad-serving-mechanic section below for how this stays safe (it never *injects* an irrelevant result, only adds a Sponsored tie-break to results that already organically matched).
- **Pricing is CPM-only for v1, not CPC — a deliberate call, not the obvious default**: see `app/core/campaign_pricing.py`'s module docstring for the full reasoning; short version: real click-fraud-resistant CPC billing (rate limiting per viewer/session, fraud heuristics, a dispute window) is a materially bigger scope than either this round or this fast-follow phase budgets for, whereas CPM billing on impressions already needed a race-safe atomic guard regardless (the PM's own ask) and extends naturally to being the sole billing lever. Clicks are still **recorded** (`Campaign.click_count`, analytics-only) so PROJECT_BRIEF.md's Advertising Analytics "clicks" bullet is satisfied without taking on CPC's fraud-resistance scope — flagged explicitly as a fast-follow-of-the-fast-follow, not forgotten. `cpm_kes` is a **platform-wide flat rate** (`CPM_KES = KES 500/1,000 impressions`, an obviously-fake round test number in the same spirit as `FEATURED_PRICING`'s KES 500/1,500 tiers), not an advertiser-chosen bid — a real bidding/auction mechanism is Phase 2+ scope; snapshotted onto `Campaign.cpm_kes` at creation time so a future rate change never retroactively alters a running campaign's economics (same reasoning as `FeaturedPurchase.amount_kes`).
- **Budget is a real prepaid balance, not a snapshot**: `budget_kes` (running total ever funded) and `spent_kes` (running total billed) are both plain `Numeric(12,2)` columns on `Campaign` itself — `budget_kes` is intentionally a materialized column (not a live `SUM(CampaignFunding.amount_kes)` computed on every read) because the atomic-deduction guard (see below) needs to read and compare it as a single row value inside one UPDATE's WHERE clause, not via a subquery join every time.
- **`CampaignFunding` is its own repeatable-transaction table, not a one-shot purchase like `FeaturedPurchase`** — because a campaign can be topped up more than once over its life (unlike `FeaturedPurchase`, which *is* the one-shot purchase). Byte-for-byte the same STK-Push-correlation shape/fields/validation posture as `FeaturedPurchase` (`checkout_request_id` unique+indexed, `merchant_request_id` cross-checked, `payer_phone`, `mpesa_receipt_number`/`result_code`/`failure_reason`) — see that model's docstring, which applies unchanged here. One real difference: `amount_kes` is **advertiser-chosen** at funding time (validated against a `MIN_FUNDING_KES` floor, KES 200 — an operational-sanity minimum, not a business decision), not a snapshotted pricing tier, since a top-up has no "tier."
- **`CampaignFundingStatus` is its own enum, deliberately not a reuse of `FeaturedPurchaseStatus`** even though the three values (pending/completed/failed) are identical — unlike Product/Video's shared `ModerationStatus` (the literal same review pipeline, reused on purpose), `FeaturedPurchase` and `CampaignFunding` are two independently-owned features with their own migration-owned enum-name strings; cross-importing would couple two otherwise-unrelated features for zero savings (each still needs its own `Enum(..., name=...)` mapped_column either way).
- **`app/services/mpesa.py` is reused wholesale, untouched** — `PaymentBackend`/`DarajaMpesaBackend`/`get_payment_backend()`/`to_msisdn()` are provider-agnostic and campaign-agnostic exactly as designed; the campaign-funding endpoint (handoff, below) calls `get_payment_backend().initiate_stk_push()` the identical way `featured_purchases.py` already does.

**Lifecycle state machine** (`CampaignStatus` in `app/models/campaign.py`, full transition-table docstrings live on the enum and its `REJECTABLE_STATUSES`/`APPROVABLE_STATUSES`/`FUNDABLE_STATUSES`/`COMPLETABLE_STATUSES` tuples — summarized here):

```
PENDING_REVIEW --approve--> APPROVED or ACTIVE (see funding-independence below)
PENDING_REVIEW --reject--> REJECTED
APPROVED/ACTIVE/PAUSED/EXHAUSTED --reject--> REJECTED
REJECTED --approve--> APPROVED or ACTIVE
APPROVED --[funding completes, budget>spent]--> ACTIVE
ACTIVE --pause--> PAUSED
PAUSED --resume--> ACTIVE (unconditional; a paused campaign never spends)
ACTIVE --[spend reaches budget, atomic]--> EXHAUSTED
EXHAUSTED --[funding completes, budget>spent]--> ACTIVE
any non-COMPLETED state --complete--> COMPLETED (terminal)
```

Judgment calls made here, each worth a real business reason:

- **Funding and moderation are independent, confirmed as the PM's own instinct**: a campaign accepts a `CampaignFunding` top-up in almost every status (`FUNDABLE_STATUSES` — everything except `COMPLETED`, the owner's own deliberate end) regardless of moderation state, but only ever actually **serves** (bills impressions) once it is *both* approved *and* funded (`budget_kes > spent_kes`), checked at whichever of those two events happens second: `app/services/campaign_billing.py`'s `resolve_status_after_approval()` (call this from the approve endpoint instead of hardcoding `APPROVED`) checks funding-at-approval-time, and `apply_campaign_funding()` (call from the M-Pesa callback) checks approval-at-funding-time. Neither path can be skipped or done twice — a campaign that's both approved and funded is `ACTIVE` no matter which order the two things happened in.
- **`EXHAUSTED` and `COMPLETED` are deliberately different terminal-ish states, not the same state under two names**: `EXHAUSTED` is automatic (ran out of money) and recoverable — a top-up revives it straight back to `ACTIVE`. `COMPLETED` is the owner's own deliberate "I'm done" action and is truly terminal — it does not auto-reactivate on funding, cannot be edited/approved/rejected/funded again. This distinction matters commercially: an advertiser whose campaign quietly exhausted mid-month should be able to top up and keep running without recreating anything; an advertiser who chose to stop a campaign early shouldn't have a stray top-up (or an admin mistake) silently resurrect it.
- **Approve/reject reuse this codebase's existing moderation-relax convention directly, confirmed as the right call, not just assumed**: per the 2026-09-04 "approve/reject can now act on already-reviewed content" entry above, reject is allowed from `PENDING_REVIEW`/`APPROVED`/`ACTIVE`/`PAUSED`/`EXHAUSTED` (409 only from the already-`REJECTED` double-click case) and approve is allowed from `PENDING_REVIEW`/`REJECTED` (409 from anything already-approved-in-some-form) — a moderator finding a policy violation on a *running, spending* campaign can pull it down immediately, exactly like an approved product/video/business. `EXHAUSTED` is deliberately reject-able too (not just active ones) — otherwise a naturally-exhausted-but-policy-violating campaign could sit unrejected and later be silently revived by an innocent top-up.
- **Editing a campaign re-triggers review, same policy as products/videos**: `PATCH /campaigns/{id}` (handoff) resets `APPROVED`/`ACTIVE`/`PAUSED`/`EXHAUSTED` back to `PENDING_REVIEW` on any owner edit to `name`/`category_id`/`county` (admin edits exempt, same carve-out as products/videos) — changing an ad's targeting is exactly the kind of change PROJECT_BRIEF.md's Content Moderation section says must be reviewed before it's live again, and it immediately stops the campaign from serving (only `ACTIVE` serves) until re-approved. `product_id`/`business_id` (the target) are immutable after creation — same as `FeaturedPurchase` never allowing its target to change; an advertiser who wants to promote a different product creates a new campaign.

**Ad-serving mechanic — the hard design problem, worked through in full:**

Search/browse in this app is entirely client-side (`frontend/src/lib/searchCatalog.ts`'s `filterBusinesses`/`filterProducts` rank against data the frontend already fetched — there is no server-side search-time ad auction, and Phase 1a's existing `is_featured` tie-break already established the precedent of doing this client-side). The design here follows that precedent rather than introducing a new server-side auction endpoint, for the same "smallest thing that satisfies the requirement" reasoning `is_featured` used.

**API surface (design only — not implemented this round, see handoff):** add a lightweight `active_campaign: CampaignTargetingRead | None` field to `BusinessRead`/`ProductRead` — `{campaign_id, category_id, county}`, present only when there currently exists an `ACTIVE` `Campaign` row targeting that exact business (`product_id IS NULL`) or that exact product (`product_id = <this product>`). This is deliberately **not** a separate ad-auction call the frontend has to make per search — the client already fetches `BusinessRead`/`ProductRead` for every result it renders, so the targeting info arrives for free on the same response, and `searchCatalog.ts`'s existing `rank()` tie-break (which already reads `is_featured` off the same objects) is a natural place to extend with a second check.

**What "matches the category/location the user is browsing" means, precisely — this is the part with real design risk if left ambiguous**: the match is against the **current browse/search context** (the filters the frontend currently has applied — `SearchFilters.categoryIds`/`SearchFilters.location` in `filterState.ts`, or the implicit category of a category-browse page/rail), **not** the item's own organic category(ies) or location. A campaign with `category_id=null` matches any context; a campaign with a specific `category_id` only earns the Sponsored tie-break when the viewer is currently in that category context. Critically, **this must only ever apply a tie-break/badge to an item that already organically matched the query and any active filters** — it must never *inject* a business/product into a result set it wouldn't otherwise appear in, exactly like the existing `is_featured` tie-break in `rank()` only reorders already-filtered items and never adds new ones. This keeps campaign targeting from becoming a way to buy your way into irrelevant search results (which would undermine PROJECT_BRIEF.md's "sponsored placements... kept distinct from organic results" line — distinct in *labeling*, yes, but a sponsored result that isn't even a real answer to the query would cross from "labeled placement" into "spam"), while still letting an advertiser deliberately target a category/location their listing doesn't organically belong to (their choice, their budget) for whenever a viewer *is* browsing in a way that happens to also surface it organically (e.g. a keyword search that matches regardless of category, viewed while a category filter is also applied).

Exact frontend wiring (which page/filter-context maps to which check, how Home's category rails vs. Search's filter chips vs. an unfiltered browse each resolve "the current category/location context") is explicitly **next round's (frontend-engineer's) job**, per this round's own scope — this section defines the data contract and matching semantics that round needs, not the component code.

**Bulk-loading `active_campaign` without N+1** (handoff detail, for whoever wires `businesses.py`/`products.py`): one indexed query per list/detail call — `SELECT * FROM campaigns WHERE status='ACTIVE' AND business_id IN (...) AND product_id IS NULL` (and the product-scoped equivalent) — assembled into a `{id: CampaignTargetingRead}` dict in Python, then the transient (non-persisted) attribute `business.active_campaign = campaign_map.get(business.id)` is set directly on each ORM instance *before* it's returned from the endpoint. This works with Pydantic v2's `from_attributes=True` the same way `ProductSummary`/`ProductRead`'s existing `_derive_primary_image`/`_set_primary_image` validators already stash a computed, non-column value (`primary_image_url`) onto the raw ORM object for the response schema to pick up via `getattr` — same trick, applied at the endpoint layer instead of a schema validator here because it needs a DB query the schema layer has no session to run. Same pattern as `admin_list_categories`'s three grouped-aggregate "used by" counts (one query per relationship type, not N+1 per row).

**Visual language — reuse, don't invent**: a campaign-driven Sponsored result renders with the exact same Sponsored/Featured badge component/copy already shipped for `is_featured` (`FeaturedTag`/`Tags.tsx`'s amber styling, per the 2026-09-04 Business Dashboard entry above) — the two mechanisms (flat-fee untargeted vs. budget-based targeted) are visually identical to a viewer; only the underlying data (`is_featured`/`featured_until` vs. `active_campaign`) differs, and the frontend's tie-break logic should simply OR the two "is this sponsored" signals together, not present them differently. Flagged explicitly so the frontend round doesn't invent a second badge style.

**Impression/click recording + atomic budget deduction** (`app/services/campaign_billing.py`, shipped and live-verified this round):

`record_campaign_impressions(db, campaign_ids)` reuses the exact batch shape of `POST /businesses/impressions`/`POST /products/impressions` (a capped id-list, unauthenticated, unknown/ineligible ids silently skipped, `{"updated": N}` response) but is campaign-scoped and must additionally (a) deduct `COST_PER_IMPRESSION_KES` from `spent_kes`, and (b) atomically flip a campaign to `EXHAUSTED` the instant its spend would reach its budget — a race between two nearly-simultaneous impressions must never be able to jointly overspend. Implemented as **one** SQL `UPDATE ... WHERE status='ACTIVE' AND spent_kes + cost <= budget_kes SET spent_kes = spent_kes + cost, impression_count = impression_count + 1, status = CASE WHEN spent_kes + cost >= budget_kes THEN 'EXHAUSTED' ELSE 'ACTIVE' END` — the exact `UPDATE ... WHERE spent_kes + cost <= budget_kes` DB-level guard the brief asked for, with the exhaustion flip folded into the *same* statement/transaction (via SQL `CASE`) rather than a follow-up UPDATE, so no external reader can ever observe `spent_kes >= budget_kes` with `status` still `ACTIVE`. This is standard Postgres READ COMMITTED behavior (an UPDATE re-checks its WHERE clause against each row's latest *committed* values at the moment it takes that row's lock) — no `SELECT ... FOR UPDATE`, no elevated isolation level needed. `record_campaign_clicks(db, campaign_ids)` is the analytics-only, non-billing equivalent (plain counter, `ACTIVE`-only, no race concern since there's no ceiling to respect).

**A real bug found and fixed while verifying this, not assumed away**: the first implementation wrote the SQL `CASE`'s branch values as `CampaignStatus.EXHAUSTED.value`/`CampaignStatus.ACTIVE.value` (i.e. the lowercase `"exhausted"`/`"active"` strings) — reasonable-looking, since `CampaignStatus` mixes in `str`. But this codebase's established `Enum(SomeEnum, native_enum=False, length=N)` mapped columns actually store the Python enum member's **`.name`** (e.g. `"VERIFIED"`, `"ACTIVE"` — uppercase), not its `.value`, confirmed by inspecting the real mapped column's own `bind_processor` output directly (`Campaign.__table__.c.status.type.bind_processor(dialect)(CampaignStatus.ACTIVE)` returns `"ACTIVE"`) and by querying a real existing row (`businesses.verification_status` is literally stored as `"VERIFIED"` in Postgres, not `"verified"` — this project's own docs/decisions.md entries describing lowercase values were never actually checked against the raw column before now). Passing a bare `CampaignStatus` member into `case()`'s literal branches also does **not** reliably route through that same column-specific bind processor (`case()`'s own type-inference for a bare Python enum value resolves differently and wrote the lowercase `.value` string instead) — writing `"active"` into a column whose real stored values are uppercase silently corrupted the row after the very first successful UPDATE, and every subsequent concurrent attempt's `WHERE status = 'ACTIVE'` guard then failed to match (comparing against the correctly-uppercase-bound literal `'ACTIVE'`, which no longer equaled the just-corrupted `'active'` row). Concretely: a 40-thread concurrency test against a campaign funded for exactly 10 impressions billed only **1** of 40 attempts with the bug present. **Fix**: use the literal `.name` strings (`CampaignStatus.EXHAUSTED.name`, `CampaignStatus.ACTIVE.name`) directly in the `case()` branches, sidestepping `case()`'s type-inference ambiguity entirely by supplying exactly the string the column already stores — re-ran the identical 40-thread test and got exactly **10** of 40 billed, `spent_kes == budget_kes` exactly, `status == EXHAUSTED`, and a follow-up impression against the now-exhausted campaign correctly billed 0. This is exactly the kind of thing the task brief asked to prove empirically rather than assert — it would not have been caught by a synchronous, single-threaded happy-path check.

**Lesson for future test-writing in this codebase, worth remembering explicitly**: any test that exercises `POST /campaigns/{id}/funding` or `POST /businesses/{id}/featured-purchases` (both real, network-calling STK-Push-initiate paths) must request `fake_payment_backend` — a test that "passes locally" without it is not actually testing anything real, it's silently spending real (if free) sandbox API calls and would only be caught by CI, or not at all if `MPESA_*` happened to be unset locally too.
