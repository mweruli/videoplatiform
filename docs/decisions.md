# Architecture Decisions

Decisions made outside `DEVELOPMENT_PLAN.md` during implementation, so the team doesn't rediscover the same question. Append, don't rewrite history — add new entries below existing ones.

## 2026-08-28 — Sprint 1 foundations skeleton

**Sync SQLAlchemy (psycopg 3), not async.** The dev plan specifies SQLAlchemy 2.0 without committing to sync or async. Chose sync: this is a 5-person team shipping mostly CRUD-shaped endpoints in 12 weeks, and sync SQLAlchemy + Alembic is materially less error-prone than async SQLAlchemy (session lifecycle, greenlet quirks, async-aware everything) for that profile of work. FastAPI still serves requests concurrently via its threadpool. Revisit per-endpoint only if a specific route is a proven bottleneck — don't rewrite the whole data layer speculatively.

**Dependency management via requirements.txt / requirements-dev.txt, not Poetry/PDM.** Simplest thing that works, matches the Dockerfile directly, no lockfile tooling to teach. `requirements-dev.txt` adds pytest/ruff/mypy on top of the runtime set.

**Health check at both `/health` (unprefixed) and implicitly reachable via the same handler under `/api/v1`.** Unprefixed `/health` exists for load balancers, uptime monitors (see `docs/SETUP.md` re: UptimeRobot) and the frontend's placeholder connectivity check — those shouldn't need to know the API version prefix. Actual API capabilities live under `/api/v1/*` per the API-first architecture.

**Category model + migration included in the Sprint 1 skeleton**, seeded with the 18 launch categories from `PROJECT_BRIEF.md`, because the sprint plan explicitly lists "18 categories seeded" as a Sprint 1 deliverable and it's the natural way to prove the SQLAlchemy → Alembic → Postgres pipeline actually works end to end (rather than shipping migrations with zero tables). The Backend Engineer should extend this model (hierarchy, icon, sort order) as listing work in Sprint 2 needs it — treat the current shape as a placeholder, not a final schema.

**Tailwind v4 (`@tailwindcss/vite` plugin) instead of v3 + postcss config.** Less config surface for a fresh Vite project, same utility classes the Frontend Engineer and UI/UX Designer will use. `frontend/src/styles/index.css` defines a handful of starter `@theme` tokens (`--color-brand-*`, `--color-surface`, `--color-ink`) purely so the placeholder pages aren't unstyled — the UI/UX Designer owns the real design system and should replace these once Sprint 1–2 mockups are approved, not treat them as final.

**React pinned to 18.3.x**, not the 19.x that `npm create vite@latest` scaffolds by default today, to match the stack choice in `DEVELOPMENT_PLAN.md` exactly (React 18). If the team wants to move to 19 later, that's a deliberate upgrade decision, not a default from re-scaffolding.

**oxlint kept as the frontend linter** (what the Vite scaffold ships with today) rather than swapping to ESLint. It's fast and already wired to `npm run lint`, which is all CI needs; nothing in the dev plan mandates ESLint specifically. Revisit if a rule ESLint has and oxlint doesn't becomes a real blocker.

**Local dev docker-compose self-hosts Meilisearch** (official image, no external account) so `docker compose up` works with zero external signups. `docs/SETUP.md` flags the production decision (self-host vs. Meilisearch Cloud) as something the PM decides before Sprint 4, not something already settled.

**docker-compose maps Postgres to host port 5433, not 5432.** Verifying the stack on the tech lead's dev machine surfaced a real gotcha: a native Postgres service already listening on 5432 (unrelated to this project — common on a shared dev box) silently intercepts connections meant for the Dockerized one, causing confusing auth failures that look like a docker-compose bug but aren't. Container-to-container traffic (backend service to `postgres:5432`) is unaffected — only the host-exposed port moved. If you hit `password authentication failed` against `localhost:5432` on your own machine, this is almost certainly why; check `netstat`/`lsof` for another Postgres already bound there.

**Meilisearch compose healthcheck uses `127.0.0.1`, not `localhost`.** The official image's `wget` resolved `localhost` to the IPv6 loopback (`::1`) while Meilisearch itself only binds the IPv4 `0.0.0.0:7700` listener, so the healthcheck reported "unhealthy" (connection refused) even though the server was up and serving requests fine on IPv4. Same class of bug to watch for in any other container healthcheck that uses `localhost`.

**Local dev OTP provider defaults to `console`** (prints codes to backend logs) rather than requiring a real SMS/email provider account to run the skeleton. `AFRICASTALKING_*` config exists for when the Backend Engineer wires up real OTP delivery in Sprint 1's auth work — Africa's Talking is the default suggested provider given the Kenya market, but this isn't a locked-in vendor decision.

## 2026-08-29 — Sprint 2: Business & Product core

**Gap found: real auth (registration/OTP/login/JWT) was never actually built in Sprint 1**, despite `DEVELOPMENT_PLAN.md`'s sprint table listing "auth (OTP/JWT)" under Sprint 1. Only the `Category` model and health check exist from that sprint. Sprint 2's ownership model (a business has an `owner`, product/business CRUD is RBAC-gated) can't work with zero `User` model or way to authenticate. Rather than block Sprint 2 on the full OTP flow, this sprint adds the smallest thing that unblocks it:
- `app/models/user.py` — a real `users` table (phone + email, nullable role default `general_user`, the 7 brief roles as a `UserRole` enum) meant to be the permanent users table, not a placeholder to be replaced.
- `app/core/security.py` / `app/api/deps.py` — JWT issuance/verification and `get_current_user` / `require_roles` dependencies, reusable once real login exists.
- `app/api/v1/endpoints/auth_dev.py` — a **DEBUG-only** `POST /api/v1/dev/token` that creates-or-fetches a user by email/phone and mints a real access token for them, purely so Sprint 2's endpoints are exercisable end to end without registration/OTP existing yet. Hard-404s when `settings.DEBUG` is false, so it can never reach production by accident. **This should be deleted once real registration + phone/email OTP + login ships** — nothing else in the codebase depends on it (all other endpoints just consume the standard `Authorization: Bearer <jwt>` + `get_current_user`/`require_roles` contract, which real login will also produce).
- Flag for the Tech Lead/PM: auth is now the most load-bearing gap blocking a real demo (an actual person still can't register/log in) — worth prioritising ahead of or alongside Sprint 3.

**Business has a single primary location (county/city/address_line), not a multi-branch model.** `PROJECT_BRIEF.md` says "locations" (plural) but the design prototype's mock data and Sprint 2's scope both model one location per business. A proper multi-branch `BusinessLocation` table is a reasonable fast-follow once a real business asks for it.

**Business has one `category_id` (single FK), not a many-to-many.** The design prototype's mock data shows a business with two categories (`['Manufacturing','Construction']`), but the brief's field list says "industry/category" (singular). Products carry their own optional `category_id` independent of the owning business's, which covers most "we sell into two industries" cases without a business-category join table.

**Verification is a 2-step state machine**: business created as `unverified` -> owner calls `POST /businesses/{id}/submit-for-verification` -> `pending` -> moderator/admin calls `POST /admin/businesses/{id}/approve` or `/reject` -> `verified` or `rejected` (owner can resubmit from `rejected`). Approve/reject only succeed from `pending` (409 otherwise) — this is a real state machine, not a free-form status field, so the admin dashboard can't accidentally skip review.

**Editing an already-approved product resets it to `moderation_status=pending`** (admin edits are exempt). This means an owner fixing a typo temporarily un-publishes their own listing until re-reviewed. Chosen because PROJECT_BRIEF.md's Content Moderation section says *all* UGC/commercial content is reviewed before publication, and "reviewed once, then silently editable forever" undermines that. Flagging this because it has real moderator-workload implications once there's meaningful edit volume — easy to relax later (e.g. only re-review if price/name/specs change, not description typos) if it turns out to be too strict.

**Product `related_products` is an explicit curated many-to-many**, not an auto-computed "same business" list — a business can point a spare part at its parent equipment across categories. `GET /products/{id}` falls back to same-business approved products when nothing's curated, so the frontend always gets a non-empty rail without extra client-side logic.

**Object storage abstraction (`app/services/storage.py`) ships now, R2/Spaces account still doesn't exist.** `StorageBackend` is an ABC with `LocalDiskStorage` (writes under `backend/media/`, served via a `StaticFiles` mount at `/media`) and a fully-implemented `S3CompatibleStorage` (boto3, works against either R2 or DO Spaces — both speak S3) gated behind `settings.OBJECT_STORAGE_ACCESS_KEY` being set. Local disk is dev-only and gitignored; going live is a config change (fill in `OBJECT_STORAGE_*` in `.env`), not a code change.

**All new UUID-keyed tables (`users`, `businesses`, `products`, plus the `product_related` join table) use client-generated UUID primary keys**, matching the existing `categories` table's philosophy of "keep it simple" but diverging from its integer-serial choice — UUIDs avoid enumerable business/product ids in public URLs (`GET /businesses/{id}`) at negligible cost for this data volume. `slug` columns exist alongside for human-friendly URLs (`GET /businesses/slug/{slug}`).

**Enums stored as `VARCHAR` + Python-side `Enum` (`native_enum=False`), not native Postgres `ENUM` types** — consistent with wanting roles/statuses to stay admin-configurable later (per `PROJECT_BRIEF.md`'s "configurable admin roles") without an `ALTER TYPE ... ADD VALUE` migration each time a new status/role is needed.

## 2026-08-29 — Sprint 2 auth follow-up: real registration/OTP/login/password-reset

Real auth now exists (`app/api/v1/endpoints/auth.py`), replacing `app/api/v1/endpoints/auth_dev.py`'s DEBUG-only stub as the actual way a person registers and logs in. `auth_dev.py` itself is **not deleted yet** — kept as a DEBUG-only convenience for quickly minting tokens while testing other endpoints — but nothing in `app/api/deps.py` or any business/product endpoint depends on it specifically; they all consume the same `Authorization: Bearer <jwt>` contract real login now also produces.

**Login method: password is primary, OTP proves contact ownership (registration + password reset), not day-to-day login.** Considered "OTP-only" (fully passwordless) and "both, pick one at login time." Went with password-primary because:
- No real SMS/email provider account exists yet (`OTP_PROVIDER=console` — see docs/SETUP.md); an OTP-only login means *every* login depends on that provider working and being fast, which is a much bigger blast radius than needing it only at registration/password-reset time.
- SMS costs money per send in production; password login has zero per-login marginal cost.
- Password + bcrypt (`passlib`, already in requirements.txt) is a well-understood, standard mechanism the team doesn't have to relitigate later.
- OTP still does real work: it's the only thing that proves a phone/email actually belongs to the registrant (`is_verified` only flips true after a correct REGISTRATION-purpose code), and it gates password reset (`PASSWORD_RESET` purpose) so an attacker can't reset a password without access to the registered phone/email.
- `OtpPurpose.LOGIN` is scaffolded in `app/models/otp.py` but unused — a passless/OTP-login endpoint is a reasonable Phase 1b addition once a real, cost-acceptable SMS provider is wired in (see below), not a redesign.

**Endpoints shipped** (all under `/api/v1`, see `app/api/v1/endpoints/auth.py`):
- `POST /auth/register` — email and/or phone + password (+ optional full_name/role). Role is restricted to `SELF_REGISTERABLE_ROLES` (general_user, business_admin, advertiser, content_creator, publisher) — `platform_admin`/`content_moderator` are staff-assigned only, never self-registered. Creates the user `is_verified=False` and immediately issues a REGISTRATION OTP to whichever contact was given (phone preferred if both).
- `POST /auth/otp/request` — resend a REGISTRATION (or future LOGIN) code; 400s and points callers at `/auth/password/forgot` for PASSWORD_RESET (which has different enumeration-safety semantics, see below).
- `POST /auth/otp/verify` — verify a code; on REGISTRATION success flips `user.is_verified = True`. Single generic "invalid or expired" error for wrong/expired/exhausted codes (doesn't tell a caller which).
- `POST /auth/login` — email-or-phone + password. 401 on bad credentials, 403 if the account isn't verified yet or is deactivated.
- `POST /auth/password/forgot` — always 200 with an identical generic message whether or not the account exists (prevents using it to enumerate registered emails/phones); only actually issues+sends an OTP when the account is real.
- `POST /auth/password/reset` — email-or-phone + code + new_password, verified atomically; returns a fresh access token on success (reset doubles as login, since the caller just proved contact ownership).
- `GET /auth/me` — current user from a bearer token; didn't exist before, added because the frontend needs a "who am I" call after login/refresh and it's a one-line addition on top of the existing `get_current_user` dependency.

**Real rate limiting + attempt limiting, backed by Redis + Postgres** (`app/services/otp_service.py`): a 60s resend cooldown and a 5-requests/hour cap per (purpose, destination) via Redis keys, plus a 5-wrong-guesses-per-code cap tracked on the `otp_codes` row itself (`attempt_count`) — a code that hits the cap is burned immediately rather than allowed unlimited guesses. Only the HMAC-SHA256 hash of each code is stored (`app/core/security.py: hash_otp_code`/`verify_otp_code`), never the plaintext.

**OTP delivery kept behind an `OtpSender` abstraction** (`app/services/otp.py`), deliberately mirroring `app/services/storage.py`'s `StorageBackend` pattern: `ConsoleOtpSender` (dev default, logs the code) and a scaffolded `AfricasTalkingOtpSender` that raises `NotImplementedError` until `AFRICASTALKING_USERNAME`/`AFRICASTALKING_API_KEY` are provisioned and the actual `send()` call is filled in — no endpoint code changes needed when that happens, just implement that one method and flip `OTP_PROVIDER`. Separately, the auth endpoints echo the plaintext code back in the JSON response (`otp: {code, destination, expires_in_seconds}`) **only when `settings.DEBUG` is true** — this is what makes register → verify → login testable end-to-end today without a live phone/inbox; it's `None` in every response once `DEBUG=false`.

**What a real OTP/SMS provider integration needs to slot in later** (flag for PM): an Africa's Talking (or similar) account with API credentials in `AFRICASTALKING_USERNAME`/`AFRICASTALKING_API_KEY`/`OTP_SENDER_ID`, then implement the body of `AfricasTalkingOtpSender.send()` in `app/services/otp.py` (a `pip install africastalking` + a couple of lines — the call shape is already sketched in a comment there) and set `OTP_SMS_PROVIDER=africastalking` in the environment. No schema or endpoint changes are needed either way.

**Update, 2026-08-29 (later same day) — real email OTP delivery + per-channel provider split.** The PM provided a working SMTP account (cael.co.ke mail server) for the email channel, since SMS (Africa's Talking) isn't subscribed yet. Landed:
- `settings.OTP_PROVIDER` (single setting for both channels) split into `OTP_SMS_PROVIDER` (africastalking | console, phone) and `OTP_EMAIL_PROVIDER` (smtp | console, email) — the per-channel sender split flagged as a follow-up above. `get_otp_sender()` now takes the `OtpChannel` and picks the provider setting for that channel; `otp_service.request_otp()` calls it as `get_otp_sender(channel)`.
- `SmtpOtpSender` implemented in `app/services/otp.py` via stdlib `smtplib`/`email.message.EmailMessage` (no new dependency) — sends a real OTP email (code, purpose-specific action line, expiry pulled from `OTP_TTL_MINUTES`) using `SMTP_HOST`/`PORT`/`USERNAME`/`PASSWORD`/`FROM_EMAIL`/`FROM_NAME`/`USE_TLS`. Only handles `OtpChannel.EMAIL`; raises if misconfigured or called for PHONE, same fail-loud pattern as `AfricasTalkingOtpSender`.
- Verified against the live docker-compose stack: registering with a real email address (`OTP_EMAIL_PROVIDER=smtp`) completes a real SMTP transaction (STARTTLS + auth + 250 OK from the cael.co.ke server) with no exception; registering with a phone number is unchanged (`OTP_SMS_PROVIDER=console`, code logged + DEBUG-echoed as before). Test user cleaned up from the dev DB afterward.
- `preferred_otp_channel` (nullable `OtpChannel` column on `User`, default `NULL`) added via migration ahead of the PM's near-term idea of letting a user/admin pick SMS-vs-email independent of how they registered. Schema-only for now — no endpoint reads or writes it yet, since wiring it in means threading a `User` lookup into `_channel_and_destination()` in `app/api/v1/endpoints/auth.py` (today that function only sees whatever `email`/`phone` the request payload supplied, not the account) and deciding channel-selection precedence, which is real endpoint-behavior work, not a schema change. Flagging as the actual follow-up task; the migration itself just avoids a second schema change when that's picked up.

**Bug fixed along the way, not a design decision:** `passlib[bcrypt]==1.7.4` (already in requirements.txt from Sprint 1) crashes on its very first `hash()` call with `bcrypt>=4.1` installed (`ValueError: password cannot be longer than 72 bytes`) — a known passlib/bcrypt compatibility break, unrelated to any actual password length. Pinned `bcrypt==4.0.1` explicitly in `requirements.txt` to fix it; anyone rebuilding the backend image or a fresh venv needs this pin, not a live `pip install`.

**`users.phone` is normalized before storage/lookup** (`app/utils/phone.py: normalize_phone`) — strips spaces/dashes/parens so `"+254 711 224560"` and `"+254711224560"` resolve to the same account for register/login/OTP lookups. This is separate from `app/schemas/business.py`'s existing phone regex (business contact numbers are display-only, not an identity/lookup key, and were intentionally left as-is).

## 2026-08-29 — Isolated test database (fixing repeated demo-data pollution)

**Root cause**: `app/db/session.py` builds its SQLAlchemy engine from `settings.DATABASE_URL` eagerly at import time, and every test file does `from app.main import app` at module level with no `conftest.py` in `backend/tests/` to intervene. Whatever `DATABASE_URL` happens to be set in the invoking process wins. Inside the `backend` container, `docker-compose.yml` sets `DATABASE_URL` to the real `milestech` database — the same one `app/db/seed_demo.py` seeds for the PM's demo — so every `docker compose exec backend pytest` run (explicitly asked for repeatedly, as real end-to-end verification against the live stack) was writing test businesses/products/users straight into the demo data. This had to be manually cleaned up after at least four rounds. CI was never affected — it spins up its own throwaway Postgres service per run — this was purely a local/docker-compose problem.

**Fix**: `backend/tests/conftest.py` (new file). Pytest guarantees conftest.py is imported before any test module in the same directory is collected, so this file rewrites `DATABASE_URL` (and `REDIS_URL`) in `os.environ` — to `<original db name>_test` / Redis logical DB 15 — *before* `app.core.config.settings` or `app.db.session`'s module-level engine can ever be constructed from the un-rewritten value. This is invocation-agnostic by construction: a bare venv `pytest`, `docker compose exec backend pytest`, and a hypothetical future local run against a remote dev Postgres all go through the same file and all land on the isolated database — nobody has to remember to set an env var by hand, which is exactly how this kept recurring.

A session-scoped, autouse fixture in the same file then (a) `CREATE DATABASE`s the isolated `<db>_test` database if it doesn't already exist (connecting to Postgres's always-present `postgres` maintenance DB, autocommit — cheap, one extra sibling database in the same Postgres container/instance, no new service in `docker-compose.yml`), and (b) runs `alembic upgrade head` against it before the first test executes. Both steps are idempotent, so repeated runs just no-op the second time onward.

An explicit `TEST_DATABASE_URL` (or `TEST_REDIS_URL`) env var, if set, overrides the derived default — an escape hatch for pointing tests at a wholly separate test instance later, not needed for the current setup.

**Verified against the live docker-compose stack**: ran `docker compose exec backend pytest` twice, plus once more via the local `backend/.venv`. All three runs: 24/24 tests passed, and `milestech` (the real demo DB) stayed at exactly 6 businesses / 8 products / 1 user (the real seed data) before and after every run, while `milestech_test` visibly accumulated rows across runs (empty → 7/2/23 → 14/4/46), proving the isolation is real and not just "tests still pass by coincidence."

**Same-class risk flagged, not fixed in the same pass beyond the trivial Redis DB-index swap above**: `app/services/otp_service.py`'s Redis-backed rate limiting (`otp:ratelimit:<purpose>:<destination>` keys) would have hit the same shared-dev-Redis pollution risk as Postgres — fixed trivially alongside this change by routing tests to Redis logical DB 15 instead of the dev-default DB 0 (same instance, no new service, `conftest.py` does this the same way as the Postgres DB-name swap). **Not yet addressed**: Meilisearch has no equivalent per-test-run index namespace — if/when a test suite starts writing to Meilisearch (search integration lands in Sprint 4), it will index straight into whatever index the live dev Meilisearch instance uses unless a similar isolation mechanism (a `_test`-suffixed index, cleaned up per session) is added at that time. Flagging now so the Backend Engineer doesn't have to rediscover this when Sprint 4's search work starts writing real documents from tests.

**How to run tests locally from now on** (see also `README.md`): `docker compose exec backend pytest` (or `pytest` from an activated `backend/.venv`) — no extra flags, no env vars to set. It always targets `milestech_test` (or `<your DATABASE_URL's db>_test`), never the demo database, automatically.

## 2026-08-29 — Process incident: Business Dashboard shipped without a design pass

The Business Dashboard (and the Admin Panel build immediately following it) were dispatched to the Frontend Engineer directly, on the reasoning that they were "genuinely new UI but small/contained enough to build within the existing design system, use your judgment on layout." The PM correctly rejected the result: *"That's not a Dashboard. A dashboard should have a Sidebar, navbar and footer — what I'm seeing is just a webpage."*

The mistake: reusing the consumer site's `TopNav`/`BottomNav` shell and stacking content in it is not a substitute for actual dashboard/internal-tool layout — sidebar navigation, a dedicated top bar, and a footer are a different paradigm from the public browsing shell, not a styling detail that "using the existing tokens" covers. Getting the colors/type/components right while skipping this meant the screen technically matched the design system and still completely failed on layout.

**Fix**: a real design pass for a shared internal-tool shell (sidebar + top bar + footer, role-aware nav items) covering both Business Dashboard and Admin Panel, then both get rebuilt into it — the data-fetching/mutation logic (`useDashboard.ts`, the admin queue hooks) is expected to carry over largely unchanged; this is a container/layout rebuild, not a feature rebuild. Also added an explicit rule to `.claude/agents/frontend-engineer.md`: dashboard/internal-tool screens always need a design spec, full stop — "use your judgment, stay within the design system" is not license to skip that, even when it's the orchestrator (not just the PM) who frames it that way.

## 2026-08-30 — Sprint 3: Video model, upload/moderation, VideoBackend abstraction

Backend video pipeline for PROJECT_BRIEF.md's "Video & Shorts Platform" module now exists (`app/models/video.py`, `app/api/v1/endpoints/videos.py`, admin moderation added to `app/api/v1/endpoints/admin.py`), closing Sprint 3's must-ship gap — the frontend has been running the video-first thesis on fixture data since Sprint 1.

**`VideoBackend` abstraction (`app/services/video.py`) mirrors `StorageBackend`/`OtpSender` exactly**, per the established pattern: an ABC (`upload()`/`delete()`), a working dev-default (`LocalFileVideoBackend` — writes the raw uploaded file via the same local-disk mechanism images use, served back as a plain file URL good enough for a basic HTML5 `<video>` tag; no transcoding/adaptive bitrate/thumbnail-or-duration extraction, since that needs ffmpeg which isn't a runtime dependency here), and two provider scaffolds (`CloudflareStreamBackend`, `BunnyStreamBackend`) that raise a clear `RuntimeError`/`NotImplementedError` until an account exists, with the real API call shape sketched in comments — same shape as `AfricasTalkingOtpSender`. `get_video_backend()` picks a real provider only once *both* `VIDEO_API_PROVIDER` says to use it *and* that provider's credentials are actually set (`CLOUDFLARE_ACCOUNT_ID`+`CLOUDFLARE_STREAM_API_TOKEN`, or `BUNNY_STREAM_LIBRARY_ID`+`BUNNY_STREAM_API_KEY`), otherwise it degrades to the local backend — a dev setup with the default `.env.example` config never 500s for a missing third-party account.

**Video moderation reuses `Product`'s `ModerationStatus` enum directly** (imported into `app/models/video.py`, mapped to its own `video_moderation_status` VARCHAR-backed column) rather than a parallel enum with identical `pending`/`approved`/`rejected` values — same states, no reason to duplicate the type. Upload → owner-gated (business owner or platform admin, same `_can_manage` pattern as products/businesses) → `pending` → admin/moderator `POST /admin/videos/{id}/approve|reject`, byte-for-byte the same shape as the existing business/product moderation endpoints (same `require_moderator` gate, same reject-with-reason schema, same "can only transition from pending, 409 otherwise" state machine).

**Editing an approved video resets it to `pending`** (admin edits exempt) — same policy as products, for the same Content-Moderation-section reasoning already flagged in the Sprint 2 entry above.

**`GET /videos` deliberately repeats products.py's `include_unapproved` pattern *and* its bug-fix**: `is_active` is enforced unconditionally regardless of `include_unapproved`, so an owner's soft-deleted video can't reappear in their own dashboard the way the products regression did (see `test_removed_product_stays_gone_from_owner_view`) — `test_removed_video_stays_gone_from_owner_view` guards the video equivalent from day one instead of needing a second incident to catch it.

**View counting is a dedicated `POST /videos/{id}/view` endpoint, not increment-on-GET.** `GET /videos/{id}` stays side-effect-free (no accidental inflation from link-preview bots, prefetching, or the owner's own dashboard re-fetching the record); the endpoint only increments for videos that are currently `approved` + `is_active` (404 otherwise), so a pending/rejected/removed video can't accumulate views before or after it's actually public. No per-viewer de-duplication — that's an analytics-hardening concern for later, not launch-blocking for Phase 1a's "basic counts" scope.

**A video can reference a product it showcases (`product_id`, optional), validated to belong to the *same* business as the video** (`_resolve_product()` in `app/api/v1/endpoints/videos.py`) — an endpoint-level invariant, not a DB constraint, since nothing in the schema stops a video's `product_id` FK from pointing at another business's product otherwise. Deliberately follows the "no explicit validation beyond the FK" pattern products.py already uses for `category_id`, since category assignment has no cross-business-ownership question to get wrong the way product association does.

**Seed data: 3 real (tiny, ffmpeg-generated) MP4 clips + JPG thumbnails checked into `backend/app/db/seed_assets/videos/`**, one per business referenced in `docs/decisions.md`'s existing seed set (AquaTank manufacturing, Solaris inverter demo, SunFlow irrigation) — `seed_demo.py` uploads them through the real `VideoBackend` (not a hand-written DB row pointing at a path that may not exist), so a fresh clone/CI run always has something the frontend can actually fetch and play, not just metadata. Files are ~6-9KB each (4s, 640x360, `libx264`, no audio) — generated with `ffmpeg` via the `imageio-ffmpeg` PyPI package (bundles a static binary; not a runtime dependency of the app, only used once to produce these three checked-in files) since no ffmpeg binary or managed video API account is available in this environment. The repo-wide `*.mp4`/`media/` gitignore rule now has an explicit `!backend/app/db/seed_assets/**` exception so these specific files aren't accidentally excluded.

**What a real Cloudflare Stream / Bunny Stream integration needs to slot in later** (flag for PM, same shape as the Africa's Talking OTP flag above): provision the account, fill in `CLOUDFLARE_ACCOUNT_ID`/`CLOUDFLARE_STREAM_API_TOKEN` (or `BUNNY_STREAM_LIBRARY_ID`/`BUNNY_STREAM_API_KEY`) in the environment, implement the body of that backend's `upload()`/`delete()` in `app/services/video.py` (the real API call shape is already sketched in comments — Cloudflare's direct-upload endpoint or Bunny's create-then-PUT flow), and set `VIDEO_API_PROVIDER` accordingly. ## 2026-08-30 — Product/Video: single `category_id` -> many-to-many `categories`

Reverses this sprint's own earlier decision ("Business has one `category_id`... Products carry their own optional `category_id`") for **Product and Video only** — the PM hit a real case (a video genuinely belonging in more than one category) that a single FK can't express. **Business is unchanged**: still one `category_id`, not raised, not in scope.

**Schema**: `products.category_id`/`videos.category_id` (single FK, nullable) replaced by `product_categories`/`video_categories` join tables (`{product,video}_id` + `category_id`, composite PK, `ON DELETE CASCADE` both directions), matching `product_related`'s existing self-referential-M2M style exactly (`app/models/product.py`, `app/models/video.py`). `Product.categories`/`Video.categories` are `lazy="selectin"` relationships, zero-or-more, no ordering guarantee beyond insertion order in a given request. Migration `7f3a9c1d2b4e_product_video_multi_category.py`: creates both join tables, copies each row's existing single `category_id` into the join table as its first category, *then* drops the old column — verified against the live dev DB that the PM's real "Ramco Group" business's video ("Printing project", category_id=1/Manufacturing) and product ("Mweruli Machine", category_id=3/Education) both landed in the join tables with their original category intact, and total business/product/video counts (7/10/4) were unchanged before and after `alembic upgrade head`. Downgrade path exists (best-effort: picks the lowest category_id per row when collapsing back to a single FK, since M2M -> single-FK is inherently lossy for any row with 2+ categories).

**API shape** (this is what the Frontend Engineer needs for forms/filters):
- `POST /businesses/{id}/products` and `PATCH /products/{id}`: body takes `category_ids: list[int]` (was `category_id: int | None`) — empty list or omitted means zero categories, not "inherit the business's." Max 10, deduped, order-preserving; unknown ids 400.
- `POST /businesses/{id}/videos` (multipart) and `PATCH /videos/{id}`: same field, `category_ids`. On the multipart upload endpoint it's a repeated form field (`category_ids=1&category_ids=2` / repeated `-F category_ids=<id>` in curl, or an array-of-values `FormData.append("category_ids", id)` per id from JS) — FastAPI's `list[int] = Form(...)` parses that natively, there is no JSON-array-as-single-field option here since the endpoint is multipart (file upload).
- `ProductRead`/`VideoRead` responses: `categories: list[CategoryRead]` (was `category: CategoryRead | None`) — always an array, empty if none assigned.
- `GET /products` and `GET /videos`: `category_id` query param filter is unchanged in name/shape (`?category_id=2`) but now means "has this category among its categories" (an `IN (SELECT ... WHERE category_id = ?)` exists-check against the join table) rather than equality — a product/video with 2+ categories now correctly matches a filter on *any* one of them.
- On create, `category_ids` behaves exactly like the old `category_id` for the moderation-re-review trigger: changing it on an already-approved product/video resets `moderation_status` to `pending` (same as any other reviewed-content field), unlike `related_product_ids` (curation, deliberately exempt).

**Seed data demonstrates it**: `app/db/seed_demo.py`'s `tank5000` product and its paired "Inside AquaTank" video now carry both Manufacturing (from the business) and Agriculture (`extra_category_slugs`) — a water tank is manufacturing output that also serves the agriculture market. This only takes effect on a *fresh* seed run (the script matches existing rows by slug/title and skips them, so it won't retroactively update the already-seeded single-category rows sitting in the live dev DB right now — same idempotency tradeoff the script already had for every other field, not a new gap introduced here).

Both get-or-create two fixed categories directly via `SessionLocal` (slugs `test-cat-a`/`test-cat-b`) rather than assuming `/api/v1/categories` has data — the isolated test DB (see the "Isolated test database" entry above) only runs Alembic migrations, not `app/db/seed.py`'s 18 launch categories, so no category rows exist there by default.
